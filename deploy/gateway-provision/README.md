# Early Bird preparation

This package does not install or enable its units. After both release gates and operator review, install the reviewed `prepare-native.mjs` at `/usr/local/lib/ii-tonya/prepare-native.mjs` as root-owned and not group/world writable, and install the reviewed gateway unit, `ii-tonya-early-bird-prepare.service` and `ii-tonya-migrate.service.d/30-early-bird-prepare.conf` as root-owned unit files, then reload systemd. The post-migration hook starts the separate oneshot synchronously before the deployment starts the gateway. The oneshot intentionally does not depend on or order itself after the migration unit: such an edge would deadlock the synchronous post-hook.

The operator creates root-owned mode `0600` `/etc/ii-tonya/early-bird-runtime-roles.sql` containing reviewed role provisioning and `/etc/ii-tonya/early-bird-prepare.json` containing exactly `{"database":"database_name","sql_sha256":"<sha256 of SQL bytes>"}`. The database name is a PostgreSQL identifier, not a URL or credential. Absence of the JSON file is default-off; malformed, unsafe or mismatched files fail the migration hook. Compatibility bridge profiles skip preparation.

The operator also creates root-owned mode `0600` `/etc/ii-tonya/early-bird-code-manifest.json` as compact JSON with exactly `source_sha` and `files`: `source_sha` is the 40-character selected release SHA, and `files` maps each of the 11 fixed gateway and preparation paths named in `prepare-native.mjs` to its reviewed SHA-256. No extra paths or keys are accepted. The helper reads only the selected `ii_tonya`-owned release, verifies every byte against this manifest, and copies only those public code files to `/var/lib/ii-tonya-yookassa-code/<source_sha>`. The root-owned code directory is world-readable and not group/world writable. Only after database and gateway-state preparation succeeds does it atomically change `current`; the gateway unit reads code from that directory. Never include credentials in the published files or grant the gateway access to the application account or runtime environment.

On each gateway start, the root-owned helper's `--select-code-only` mode checks the selected application's source and provenance, then verifies the root-owned, per-version manifest and all 11 stored file hashes before switching the code pointer. It neither runs SQL nor initializes gateway state. This permits rollback to a previously published version; if that version is absent or damaged, gateway startup fails closed and requires operator repair. Preparation is ordered before gateway start without adding a dependency back to the migration unit.

For a genuinely pristine gateway only, the operator creates `/var/lib/ii-tonya-yookassa/.initial-state-authorized` as root-owned mode `0600`. The gateway-owned directory must contain no existing lock, journal or nonce state. The marker is consumed only after PostgreSQL readiness, state creation and nonce-registry creation all succeed. A missing marker requires existing, valid state and a nonce registry bound to the current authentication key. Partial initialization and key rotation require manual review; do not delete or recreate state to recover automatically.

Preparation requires the gateway unit to be loaded and inactive with no main PID. It provisions SQL through local PostgreSQL peer authentication and passes no password on the command line. It does not activate the gateway, send a payment, create an application administrator or establish MFA. Install and rollout require the separate release, credential, role, network-fence and live-provider checks.
