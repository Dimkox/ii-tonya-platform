# DEC‑PLT‑004 — Правило минимальной матрицы данных и отдельных проверяемых согласий

Профильная проверка (выполнена профильным агентом по поручению владельца; владелец выбрал **вариант A**).
Запись фактов: `.memlog.md` от 2026‑09‑16. Основание для переноса в SPEC/реестр — после подтверждения
владельцем §8. Правовые номера норм сверяются по действующей редакции перед публикацией (Приложение А).

**Строка для реестра:** DEC‑PLT‑004 = вариант A: закрытая минимальная матрица данных (§2), закрытый
перечень целей/оснований (§1), отдельное проверяемое согласие на передачу эксперту (§3), запрет каналов
с незакрытой юрисдикцией (§4), числовые retention‑лимиты (§5). Инвариант продукта: **специальные
категории 152‑ФЗ и ПД третьих лиц не хранятся никогда** — единственный непротиворечивый способ удержать
запрет трансграничной передачи (C006) и раздельность согласий. Пункты A005, конфликтующие с матрицей
(дети/внуки, семейное положение, соцстатус/уровень жизни, возраст/пол/дата рождения), **снимаются из
спецификации**, а не переносятся в хранение.

## Разрешение коллизий

- **A005 vs C074/C006:** приоритет у C074/C006. «Постепенность» сбора — не правовое основание.
- **A005 vs Политика §5.1.1:** «дети/внуки» и «соцстатус» отсутствуют в публичном перечне категорий → их сбор = обработка сверх объявленного → **удаляются из продукта**.
- **C005 («начало диалога = согласие»):** признано **недостаточным основанием** для всего, кроме минимума на исполнение самого запроса; с 01.09.2025 «вшитое» в акцепт/пользовательское соглашение согласие недействительно. Блокирует правку публичных текстов (PLT‑012).
- **C006 (трансграничная передача запрещена):** §11.3 Политики уже опубликован → каналы с незакрытой юрисдикцией **не активируются**.
- **C009 («cookies не идентифицируют»):** фактически неверно (IP + cookies + id бота = ПД); правится в PLT‑012.

## §1 Правовые основания по цели (152‑ФЗ: ч.1 ст.6 закрыт; «законного интереса» нет)

- Подбор в объёме запроса — **договор** (п.5 ч.1 ст.6), без отдельного согласия.
- Персонализация/профиль, диагностика, чекапы, промо‑рассылки, cookies‑аналитика, публикация отзыва/карточки — **отдельное согласие** (п.1 ч.1 ст.6, и для распространения — ст.10.1), каждое со своим `consent_type`.
- Фискализация/платежи/счета — **обязанность по ФЗ** (54‑ФЗ, 115‑ФЗ, 431‑У, НК).
- Акцепт оферты валиден для договора эксперта/резидента, но НЕ заменяет согласие на маркетинг/распространение.
- Демография, соцстатус, семейное положение, состояние — **нет допустимого основания** → функция откладывается.

Инвариант №1: одна цель = один отдельный `consent_type`; один consent на несколько целей запрещён.

## §2 Минимальная матрица данных

Проектный базис: нет спецкатегорий ст.10 и нет ПД третьих лиц ⇒ не требуется письменное согласие (ч.4 ст.10) и класс УЗ‑1 (ПП №1119/приказ ФСТЭК №21); архитектура остаётся на УЗ‑2‑совместимом минимуме (`client_profiles` = 3 содержательных поля; `RAW_CONVERSATION_LOGGING`, `ALLOW_MINOR_DATA`, `MINOR_ONBOARDING_ENABLED` — выключены/ломятся при включении).

**Клиент:** `user_id`, Telegram‑связка, `display_name` (имени по выбору клиента; иначе «Клиент»), контакты (телефон/e‑mail — только если реально нужны), город (постоянно) + район (только на время активной брони), навыки ≤5 (≤500 зн), интересы ≤10 из закрытого списка, предпочтения = только `expert_id`, `expert_note` ≤2000 (гейт `expert_note`=granted), записи/брони, отзывы. ФИО — только в платёжно‑договорном контуре. **Возраст/пол/дата рождения — не хранятся** (только `adult_confirmed_at`). **Дети/внуки, семейное положение, соцстатус/уровень жизни, «история состояний», сырой текст диалога — не хранятся никогда.**

**Эксперт:** ФИО/наименование/ИНН‑ОГРНИП, контакты, квалификация (реквизиты + результат проверки + digest; **копии документов не хранятся**), опыт, услуги/цены, адрес (публично — только город+формат), ссылки, промокоды. Платёжные: расчётный счёт/IBAN + `provider_token` ЮKassa; **PAN/CVC/срок — никогда**.

**Посетитель:** поля формы (≤12 мес), IP **усечённый** (обнуляется последний октет/80 бит), браузер/страницы/время — в агрегате, только после opt‑in; cookies строго необходимые (≤30 дн.) — без согласия; аналитика — только после `cookies_analytics` (≤6 мес); маркетинг‑пиксели — **не активируются**.

Инвариант №2: у перечисленных «запрещённых» полей нет ни колонки в БД, ни ключа в профиле, ни поля в админке, ни упоминания в публичных текстах. Это конфликтует с критерием A005 → **A005 требует правки спецификации** (§8.1).

## §3 Отдельное согласие на передачу эксперту (C006 + C074)

Есть `consents(...)` + `withdrawConsentAtomically()` (append‑only, serializable, с аудитом) и handoff‑представление `BookingExpertScheduleRecord`. Не хватает purpose `expert_handoff`, фиксации объёма/получателя/момента/хеша, события отзыва и `cookies_analytics`. Расхождение: C074 обещает «контакты», реализация контакты не передаёт → правило: «контакты» = **только канал, который клиент сам выбрал для этой брони**, и только при `expert_handoff`=granted.

Механика: три независимых факта — `client_profile` / `expert_note` / **`expert_handoff`** (последний не выводится из первых и не из оплаты/диалога). Получение — после выбора слота, до `reserved/booked`. `denied` **не блокирует оплату**: минимальный handoff = `{«Клиент», слот, формат, meeting_url}` без имени/заметки/контактов; если эксперт не может в таком объёме — перенос/возврат (DEC‑FIN‑006), это не отказ клиента. Область: **одна бронь = одно согласие**; опционально стоящее — 90 дней, но для одного названного эксперта. Текст `handoff-v1` обязателен с реквизитами: оператор (ИП Кравцова Т.М., ИНН 683102264735), **персонально названный получатель**, список передаваемых данных, цель `{reservation_id}/{starts_at}`, указание на отдельность и отзываемость (до визита), срок у получателя. Отзыв — новый `denied`-ряд + outbox `booking.handoff_revoked`, мгновенно (тот же запрос читает `null`/«Клиент»); отзыв `expert_note` ⇒ отзывает `expert_handoff`, но не наоборот.

Новые поля аудита в `consents`: `decided_at, text_hash(sha256), scope_fields(jsonb, ≤5, из словаря), recipient_type, recipient_id, recipient_disclosed_name, reservation_id, channel, ip_address(усечённый), user_agent_hash, correlation_id, withdrawn_at, withdrawal_receipt_uri, evidence_uri`. Констрейнты в БД: частичный unique (≤1 `granted` на reservation+type); `granted ⇒ text_hash/scope_fields/recipient_type/evidence_uri not null`.

Инвариант №3: ни байт ПД не уходит к эксперту/Planerka без строки granted по этому чек‑листу; выборка «передача без предшествующего granted» = 0 строк.

## §4 Трансграничная передача и локализация (C006, ч.5 ст.18 242‑ФЗ, ст.12)

Режим (а) — хранение/обработка ПД граждан РФ только в БД на территории РФ (действует даже без «передачи»); режим (б) — передача иностранному лицу требует письменного согласия + процедуры РКН, а §11.3 закрывает его полностью. Раскрытие названному эксперту = предоставление (не распространение, ст.12 не включает), но если экспертное лицо иностранное — ст.12 включается. Все внешние флаги сейчас `false` — решения принимаются до первой строки ПД.

## §5 Retention и права субъекта (ратификация `data-retention.md`)

Идентификация — 24 мес неактивности → псевдонимизация; согласия/аудит — +3 года после удаления учётки (ст.196 ГК); профиль — ≤24 мес, при отзыве немедленно; метаданные сообщений — 3 года; брони/платежи — 5 лет (115‑ФЗ/НК/431‑У); платёжные артефакты ЮKassa ≤400 дн., unbound — 0; данные форм ≤12 мес; cookies аналитика ≤6 мес, necessary ≤30 дн.; усечённый IP ≤6 мес; медиа ≤12 мес; backup — 35 дн. с receipt. Спецкатегории/дети/семейное/соцстатус/ДР/пол/возраст/здоровье — **0, создание запрещено**.
Права (ст.21): каналы «Тоня, мои данные»/e‑mail/почта; идентификация по Telegram‑id + 2 атрибута, **паспорт не запрашиваем**; ответ ≤30 к.д.; внутренние SLA: отзыв — мгновенно, блокирование ≤1 р.д., уточнение ≤7 р.д., удаление ≤5 р.д., receipt обработителей ≤10 р.д., backup‑receipt день 35. Приоритет «отзыв vs удержание»: отзыв **не** отменяет брони/платежи за 5 лет (основание — договор/ФЗ, не согласие) и не трогает ряды согласий; отзыв **обязан** остановить профиль/`expert_note`/`client_messaging`/`follow_up`/`cookies_analytics`/`expert_handoff` и любые передачи. Формула: **«отзыв останавливает обработку, но не аннулирует учётный факт»**. Получатель обязан удалить переданное за ≤3 р.д. по требованию и не хранить >30 дней после визита; повторная передача/CRM у получателя запрещены.

## §8 Красные линии — не решения юриста, нужна подпись владельца

1. **A005 vs матрица:** убрать «дети/внуки, семейное положение, соцстатус/уровень жизни, возраст/пол/ДР» целиком? Юрист — да (единственная не‑РФ‑рисовая конфигурация), но это режет персонализацию/«диагностику» и лишает перс‑quote'а (цена — из диапазонов эксперта и скидок, не из дохода клиента — DEC‑FIN‑021/022). Требует снять/переформулировать критерий A005.
2. **Telegram — остаётся каналом?** (а) остаётся с §4‑границами; (б) уход в РФ‑канал (снимает с релиза клиентский контур PLT‑004/005/010/016); (в) гибрид (запись/платежи в Telegram, чувствительные тексты — в web с РФ‑хостингом). Все три равноправны юридически при корректных согласиях → это продукт/аудитория.
3. **Sheets/Make — отключить навсегда или заменить** (РФ‑таблица с поручением)? Это бюджет и roadmap, но персонифицированные `Clients`/`Waitlist` в Sheets оставить нельзя.
4. **Микро‑чекапы / «история состояний» — сохраняем?** Правило — «только in‑session, без хранения»; владелец может отложить функцию (цепляет DEC‑PLT‑008, DEC‑EXP‑006) или сузить до бытовых/организационных формулировок.
5. **18+: достаточно ли самодекларации?** Самодекларация (+реактивный бан) vs верификация документом. Красная линия: **верификация «через паспорт в чате» юристом не будет одобрена** ни при какой конфигурации.
6. **Цена миграции T0‑B:** 60‑дневная кампания «пересогласовать или удалить» обнулит профиль/`expert_note` у не нажавших и остановит промо/чекапы (churn). Можно ужесточить (T0+30) или смягчить «поле остаётся, но не читается» — последнее приемлемо **только** при доказанном нулевом чтении (тесты №6/№7), не по намерению.
