## Пункты задачи

- [ ] **REQ-FIN-001.01** — Определить целевую когорту и политику client access: существующие legacy_package_v1 и free_client_v2 нельзя массово заменить без версионированного миграционного контракта.
  - Проверка: Решение описывает назначение новых и существующих пользователей и откат без переприсвоения истории.

- [ ] **REQ-FIN-001.02** — Если выбрана пакетная модель, списание каждого входящего, исходящего и системного сообщения, включая уведомление, reminder, кнопку и аудио, равно 1 unit; Telegram-бот эксперта не списывает клиентские units.
  - Проверка: Матрица классов сообщений определяет charge=1 либо явное исключение для каждого класса; экспертский Telegram не изменяет баланс клиента.

- [ ] **REQ-FIN-001.03** — Пакетное списание выбирает активный пакет с положительным остатком и ближайшим package_end_date; при отсутствии подходящего пакета поведение заглушки и её тарификация определяются явно.
  - Проверка: Тест с двумя пакетами списывает тот, у которого раньше окончание; тест нулевого баланса подтверждает выбранное поведение заглушки.

- [ ] **REQ-FIN-002.01** — Сохранить варианты исходного каталога: «Знакомство» 80–100 сообщений без срока и без купонов; «Старт» 500, «Базовый» 1000, «Глубокий» 1500, «Максимальный» 2000 сообщений.
  - Проверка: Решение фиксирует одно точное число для «Знакомства»: 80 или 100.

- [ ] **REQ-FIN-002.02** — Для платных пакетов выбрать один срок: 60 календарных дней по ранним правилам либо 30 календарных дней по V5/файлу 05; определить момент старта и часовой пояс.
  - Проверка: Правило вычисляет expiresAt из оплаченного timestamp в заданном часовом поясе и задаёт историческую совместимость.

- [ ] **REQ-FIN-002.03** — Связать каждый платный пакет с точным купонным начислением: Старт 1000, Базовый 2000, Глубокий 3000, Максимальный 4000, либо вывести его только из утверждённой x2-формулы и подтверждённых цен пакетов.
  - Проверка: Для каждого продаваемого SKU определены price, message grants, coupon grants и срок; нет невычисляемого значения без цены.

- [ ] **REQ-FIN-003.01** — Напоминание об окончании пакетного доступа отправляется единым сообщением с истекающим пакетом и остатками других пакетов, выбирает ближайший дедлайн и не повторяется для одного package_id. Источник задаёт группировку по client_id, проверку last_reminder_sent!=package_id и запись этого маркера после успешной отправки; ledger/outbox должны исключать двойную отправку или debit при сбое между этими шагами.
  - Проверка: Повторный scheduler-run не создаёт второе уведомление для того же package_id.

- [ ] **REQ-FIN-003.02** — Выбрать точную временную семантику: «ровно за 3 дня» либо сканирующее окно days_until 2–4; определить округление, расписание job и то, списывается ли само напоминание. Исходный планировщик запускается раз в 24 часа; варианты напоминания клиентскому пакету за 14 и 7 дней удалены в этом сценарии. В этой версии исходника reminder стоит одну единицу; отличие от действующей бесплатной system-message policy разрешается DEC-FIN-001, а не считается отсутствующим требованием.
  - Проверка: Boundary-тесты на 2, 3 и 4 дня дают утверждённый результат.

- [ ] **REQ-FIN-004.01** — Клиентские купоны начисляются x2 от оплаты пакета; 1 купон = 1 ₽ исключительно частичной оплаты рекомендованной услуги эксперта или мероприятия. Примеры исходной x2-модели: 500→1000, 1000→2000, 2000→4000, 5000→10000; это один вариант начисления, пока DEC по каталогу/купонам открыт. Применение купона требует активной брони;24ч/72ч и очередь из A031 реализуются TASK-PLT-001/002.
  - Проверка: Оплата 1000 ₽ начисляет 2000 купонов; расчёт услуги использует курс 1:1.

- [ ] **REQ-FIN-004.02** — Купоны не являются деньгами, не обмениваются и не выводятся; передача запрещена, кроме явно утверждённых исключений.
  - Проверка: API не имеет операции вывода/обмена купонов и отклоняет перевод между пользователями без утверждённого исключения.

- [ ] **REQ-FIN-004.03** — Выбрать срок купона: 90 календарных дней либо 45 календарных дней с начисления; после истечения купон аннулируется без восстановления, а правило возврата услуги с уже использованными купонами фиксируется отдельно.
  - Проверка: Boundary-тест на expiresAt запрещает расход после утверждённого срока и сохраняет неизменяемый ledger.

- [ ] **REQ-FIN-004.04** — Определить способ частичного списания: исходные варианты — один купон на эксперта/мероприятие и запрет двух на одну услугу, максимум 1000 в тестовой демо-выдаче, либо лимит эксперта обычно 20–50% цены; остаток оплачивается деньгами.
  - Проверка: У каждой услуги есть утверждённый cap/способ задания cap; quote разбивает сумму на coupon и cash без отрицательных значений.

- [ ] **REQ-FIN-005.01** — Каждому клиенту назначается максимум один бессрочный персональный код promo_XXXX; новый клиент получает 500 купонов при регистрации по валидному коду.
  - Проверка: Код уникален в выбранной нормализации регистра; повторная регистрация/повторное применение не начисляет второй бонус.

- [ ] **REQ-FIN-005.02** — Пригласивший получает 500 купонов только после первой оплаты пакета приглашённого; возврат этой оплаты аннулирует награду пригласившего.
  - Проверка: Первая успешная оплата создаёт ровно одну награду, продление не создаёт вторую; возврат создаёт reversal.

- [ ] **REQ-FIN-005.03** — Определить антифрод, самореферал, нормализацию кода, связь дублей и event idempotency для регистрации, оплаты и возврата.
  - Проверка: Technical design перечисляет reject-коды и idempotency keys для каждого события.
