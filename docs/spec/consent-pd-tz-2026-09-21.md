# ии-Тоня: согласия и защита персональных данных

## Техническое задание на адресную доработку существующей платформы

**Версия:** 1.0 • **Дата:** 21 сентября 2026 года • **Статус:** подготовлено к согласованию; не является разрешением на включение production-интеграций.

**Заказчик:** владелец проекта II-TONYA. **Инфраструктура по сообщению заказчика:** FirstVDS, сервер в Москве. **Репозиторий:** Dimkox/ii-tonya-platform. **Проверенная базовая ревизия:** `cb07bd1821d8106b0b0088b17bcf305662a1b792`.

**Главное решение:** для обычных персональных данных — отдельный документ и одно нажатие «СОГЛАСЕН» на сайте либо в боте. Без бумажных согласий, SMS-подписания, паспорта и дополнительной галочки. Доказательства, ограничения передачи и отзыв реализуются на сервере. Независимые дополнительные цели не подключаются скрытно этим же нажатием.

**Граница результата:** ТЗ охватывает известные риски согласий, локализации, интеграций, чувствительных данных, аналитики, доступа, удаления, миграции и запуска. Разработка устраняет технические дефекты; документы оператора, фактические условия провайдеров и применимость специальных норм подтверждаются отдельно. Отсутствующее подтверждение не заменяется отметкой разработчика «проверено».

## 1. Цель, ограничения и объём работ

**SCOPE-01.** Доработать существующие web- и Telegram-интерфейсы, механизм согласий, privacy-service, точки внешней отправки и эксплуатационные регламенты. Сохранить PostgreSQL как источник бизнес-состояния и существующие очереди. Не создавать параллельную базу согласий, новый транзакционный backend или отдельный микросервис ради этой задачи.

**SCOPE-02.** Не изменять тарифы, остатки пакетов, финансовый ledger, правила расчёта стоимости, реферальные начисления, идемпотентность бронирования и reconciliation. Защитные проверки могут ограничить конкретную обработку, но не должны переписывать финансовые факты. Новый локальный AI, перенос всей платформы и покупка GPU в обязательный объём не входят.

**SCOPE-03.** Сохранение Selarti и Telegram является целью, а не заранее подтверждённой законностью. При неподтверждённом основании блокируется затронутый маршрут; доступные законные функции продолжают работать. Нельзя автоматически переключаться на другого зарубежного поставщика.

**SCOPE-04.** «Один клик» означает одно осознанное действие для показанного согласия. Не означает разрешение одновременно на оферту, рекламу, публикацию отзывов, любую передачу и обучение моделей. Дополнительные согласия появляются только при вызове соответствующей функции. Необязательная аналитика и маркетинг по умолчанию выключены и не усложняют первый вход.

**SCOPE-05.** Согласие не подменяет авторизацию, оплату, электронную подпись в случаях обязательной письменной формы или разрешённость канала. Вход в существующий кабинет сохраняется отдельно; не добавлять SMS исключительно ради обычного согласия. Подтверждение платежа банком не относится к данному UX-ограничению.

## 2. Проверенная основа проекта и необходимые исправления

Проверены материалы репозитория, а не работающий сервер. В `privacy-service.ts` существуют `withdrawConsentAtomically`, `exportOwnedSubject`, `startErasureAtomically`, проверки принадлежности данных и отдельные цели согласий. В `apps/web/index.html` обнаружены немедленный запуск Метрики с Webvisor и отдельный `noscript`-пиксель. В решении DEC-PLT-004 зафиксированы российское хранение, ограничения интеграций и миграция старых согласий. Это основания для доработки, не доказательства production-соответствия. [R01–R05]

**BASE-01.** Перед реализацией составить карту существующих таблиц, маршрутов, обработчиков callback, worker и текстов. Сопоставить каждый пункт ТЗ с текущим кодом. Новые сущности, перечисленные ниже, являются логическим контрактом: сначала расширять имеющиеся, не создавать одноимённые дубликаты.

**BASE-02.** Оформить адресное изменение DEC-PLT-004 и связанных задач PLT-008/PLT-012. Не распространять следующие прежние допущения в код, публичные тексты или заключение о запуске:

| Прежнее допущение | Исправление для реализации |
| --- | --- |
| Сведения о здоровье допустимы без специального основания, если живут только в памяти | Получение и использование тоже являются обработкой. Временный признак может сам раскрывать здоровье. [S02, S03] |
| Любая иностранная передача требует именно письменного согласия | Форма определяется применимыми нормами и категориями данных; трансграничная процедура проверяется отдельно. [S01, S05] |
| В 152-ФЗ отсутствует основание защиты законных интересов | Пункт 7 части 1 статьи 6 существует, но не является универсальным основанием для любых операций. [S04] |
| «Telegram — транспорт» означает отсутствие зарубежной обработки | Проверяется весь путь, включая платформу, идентификаторы, содержание и доступ. Название роли не решает вопрос. [S03, S05, S06] |
| Нет медицинских колонок — значит известен уровень защищённости | Уровень определяется по составу системы, категориям, числу субъектов и актуальным угрозам. [S11, S12] |
| Всем обращениям можно отвечать за 30 календарных дней | Нужны разные сроки для доступа, прекращения, исправления и удаления. [S08, S09] |
| 60 дней на пересогласование разрешают прежнюю обработку | Переходное окно не создаёт отсутствующего правового основания. |
| HMAC/UUID, короткий токен или отсутствие имени означают анонимность | Связность с человеком оценивается отдельно; псевдонимизация не равна гарантированному обезличиванию. [S03] |

**BASE-03.** Сохранить более строгие принятые продуктовые ограничения, пока явно не утверждена их замена. В частности, нынешний запрет зарубежной передачи нельзя незаметно заменить новой политикой или включением флага. Данное ТЗ задаёт процедуру согласования разрешённого маршрута, а не объявляет её пройденной.

## 3. Реестр обработки и границы данных

**DATA-01.** Вести версионируемый реестр: цель → категория субъектов → точные поля → источник → основание → получатели → места обработки → срок → процедура прекращения. Владелец каждой строки указан. Обработка без утверждённой строки не активируется. Договорное основание применяется только к необходимым для договора операциям; поручение обработчику описывает данные клиентов Тони, а не только аккаунт владельца в сервисе. [S04]

| Контур | Допустимый объём для базового запуска | Граница |
| --- | --- | --- |
| Обычный клиент | Внутренний ID, выбранное имя, необходимые контакты, город, время, бюджет, формат и выбранная услуга | Не выводить демографию, доход, диагнозы и семейный статус из переписки |
| Бронирование | ID брони, специалист, слот, статус, выбранный канал связи | Никаких медицинских историй в названии события и уведомлениях |
| Эксперт | Проверенные реквизиты, квалификация, услуги, цены, рабочие контакты | Верификация и публикация — разные операции; не публиковать всё из анкеты |
| Согласия | Документ, область, субъект/сессия, решение, время, канал, доказательства | Не записывать весь Telegram update, токены и разговор ради аудита |
| AI-запрос | Минимальный контекст, необходимый для конкретного ответа | Профиль, полная история, контакты и заметка эксперту не добавляются по умолчанию |
| Платёж | Идентификаторы операций, сумма, валюта, состояние, обязательные учётные данные | PAN, CVC и банковские коды в Тоню не поступают |
| Технические события | Код операции, результат, время, безопасная корреляция | Не включать тела сообщений, вложения, секреты и персональные URL |

**DATA-02.** Первичный приём на собственном сайте направлять непосредственно в российский backend. До этой операции не отправлять формы в иностранные виджеты, системы ошибок, рекламные пиксели или внешние LLM. Проверить reverse proxy, CDN/WAF, почту, очереди, поисковые индексы, embeddings, файловое хранилище, APM, резервные копии и доступ администраторов из других стран. Одного адреса основного PostgreSQL недостаточно. [S06]

**DATA-03.** Авторитетный реестр и состояния находятся в PostgreSQL в РФ. Файлы, архивы доказательств и резервные копии — только в согласованном российском контуре; они не становятся второй независимой клиентской базой. Реестр содержит точные ресурсы, регионы и ответственных. Для FirstVDS приложить подтверждение именно арендуемой услуги и подключённых дополнительных сервисов. Сообщение владельца «Москва» является исходным условием, но не заменяет документ провайдера. [S16]

**DATA-04.** Приём Telegram update выделить в самостоятельную схему. Не считать московский webhook доказательством локализации первоначального сбора через мессенджер. До live-активации требуется заключение по фактическому потоку и статусу оператора. Техническую часть бота разрабатывать и тестировать на синтетических данных независимо от этого допуска.

## 4. Цели и документы согласий

**CONS-01.** Для обычных данных используется подтверждаемое электронное волеизъявление без заявления, что это письменное согласие или электронная подпись. Полный документ отделяется от оферты. Закон допускает доказуемую форму, если специальная форма не обязательна; доказательства обеспечивает оператор. [S01]

**CONS-02.** Сохранить существующие независимые цели из privacy-service. Их наличие в коде само по себе не доказывает, что закон требует отдельную галочку для каждой технической операции. Объединять юридические цели или массово выставлять несколько `granted` одним общим событием в этом релизе запрещено. [R04]

| Цель | Когда запрашивать | Поведение при отказе |
| --- | --- | --- |
| `client_messaging` | Перед зависящим от согласия персональным диалогом | Каталог, документы, поддержка, права субъекта и законное обслуживание заказов остаются доступны |
| `selarti_ai_processing` | Перед первым действительно необходимым обращением к Selarti | Локальные сценарии и разрешённая поддержка; зарубежного fallback нет |
| `client_profile` | При включении сохранения предпочтений между сессиями | Не накапливать необязательный профиль |
| `expert_note` | Перед сохранением необязательной заметки | Запись без заметки, если услуга может быть оказана |
| `expert_handoff` | Перед разрешённой передачей выбранному эксперту в области конкретной брони | Не передавать необязательные поля; предложить допустимый вариант обслуживания |
| `follow_up` | При включении соответствующего сопровождения | Не делать дополнительные обращения; обязательные сервисные сообщения не маскировать под эту цель |

**CONS-03.** Добавлять `cookies_analytics`, согласие на рекламу, `review_publication` и `expert_card_publication` только после сопоставления с фактической схемой проекта. Это отдельные действия по месту использования, а не стартовая анкета. Публикация персональных данных рассматривается по статье 10.1; рекламные сообщения — также по статье 18 закона о рекламе. [S13, S22]

**CONS-04.** Если необходимое действие законно выполняется на договорном или ином основании, не придумывать согласие для его прикрытия. При этом ранее существующий технический guard не обходится из HTTP-параметра: изменение модели оснований оформляется явно, с проверками чтения, записи и отправки.

**CONS-05.** Юридический контент берётся из утверждённого реестра документов. Публикация требует заполненных реквизитов оператора, цели, состава сведений, операций, получателей/обработчиков, срока и механизма отзыва. При трансграничной обработке сведения должны соответствовать разрешённому маршруту. Нельзя выпускать текст «любые данные любым третьим лицам» либо незаполненные шаблонные реквизиты.

## 5. Сайт: один экран и одно подтверждение

**WEB-01.** Публичный каталог и юридические документы доступны без принудительного согласия на необязательную обработку. При первом вызове функции, требующей согласия, показывается самостоятельное модальное окно с доступным полным текстом. Акцепт оферты, возрастная декларация и маркетинг не присоединяются к кнопке скрытно.

Предлагаемая оболочка, не замена полного юридического документа:

> **Согласие на обработку персональных данных**
>
> Перед началом ознакомьтесь с условиями обработки данных для выбранной функции Тони.
>
> **Читать полный текст**
>
> **СОГЛАСЕН** · **НЕ СОГЛАСЕН**

**WEB-02.** Не добавлять обязательную галочку перед кнопкой, SMS, загрузку документа, искусственный таймер или подтверждение прокрутки. Поддержать клавиатуру, экранный диктор, возврат фокуса, мобильный экран и читаемый текст. Открытие ссылки не означает согласия.

**WEB-03.** Закрытие окна и «НЕ СОГЛАСЕН» не создают положительного решения. Повторный запрос не навязывается при каждом посещении; он появляется при явном повторном запуске соответствующей функции. При отказе объясняется, какая именно функция недоступна, без заявления о потере оплаченных прав.

**WEB-04.** Нажатие отправляет аутентифицированную команду на backend. Только после транзакционной записи ответа `granted` интерфейс продолжает зависимую операцию. При недоступности БД, ошибке проверки или неясном результате показывать «Подтверждение не сохранено. Повторите действие». Повтор безопасен и не создаёт двойные события.

**WEB-05.** Локальный `localStorage`, cookie или UI-флаг не являются источником согласия. Для анонимной сессии используется случайный first-party идентификатор: согласие этой сессии не приписывается автоматически учётной записи другого человека. Перенос между устройствами — только после подтверждённого связывания личности/аккаунтов.

**WEB-06.** Правовой режим авторизации проверить отдельно по части 10 статьи 8 закона № 149-ФЗ. Согласие на обработку не доказывает допустимость иностранного social login. Не требовать новую авторизацию уже вошедшему клиенту только ради клика согласия. [S18]

## 6. Telegram: сообщение и inline-кнопка

**BOT-01.** Реализовать тот же выбор отдельным сообщением в личном чате: понятная цель, доступ к точной версии полного документа, «СОГЛАСЕН» и «НЕ СОГЛАСЕН». Обычный Bot API не требует отдельного mini app для такой механики. Согласием не считаются `/start`, отправленное сообщение, оплата или молчание. [S17]

**BOT-02.** До согласия разрешены только заранее обоснованные технические операции для ответа на инициированный запрос, защиты канала и показа документов. Telegram технически уже присылает идентификаторы: нельзя обещать отсутствие любого получения данных до кнопки. Исходный текст не сохранять в профиль/логи и не передавать AI в ожидании будущего согласия. Основание минимального приёма описать отдельно. [S03, S04]

**BOT-03.** Callback связывается на сервере с пользователем `from.id`, личным чатом, безопасным идентификатором бота, предложенным документом, целью, областью и одноразовым токеном. `callback_data` содержит только короткий непрозрачный идентификатор и укладывается в 1–64 байта. Подпись текста сообщения или `username` не заменяют проверку на сервере. [S17]

**BOT-04.** Проверять подлинность webhook, в том числе штатный secret header; не сохранять его, токен бота и секретный `botKey` в доказательствах. Пересланные кнопки, callback другого человека, групповые чаты, просроченный токен и подменённая область отвергаются. Повтор Telegram update идемпотентен.

**BOT-05.** Отвечать на callback без ложного успеха. Сообщение «Согласие сохранено» допустимо только после записи. Удалить или отключить обработанную клавиатуру; устаревшая кнопка не может повторно включить отозванное согласие. При новой версии показать новый документ, а не перепривязать старую кнопку.

**BOT-06.** IP источника webhook принадлежит сетевой стороне Telegram и не считается IP пользователя. Не придумывать browser user agent или геолокацию клиента из webhook. В доказательствах отмечать такие поля как недоступные.

**BOT-07.** Обеспечить пункты «Мои согласия», «Отозвать», «Мои данные», «Удалить данные», «Поддержка»; команды `/privacy`, `/consents`, `/revoke`, `/delete_me`, `/stop` являются предлагаемыми алиасами существующих команд. `/stop` немедленно подавляет необязательную коммуникацию. Блокировка бота останавливает попытки доставки, но не создаёт вымышленное подписанное заявление об удалении всего аккаунта.

**BOT-08.** При правовом запрете на использование иностранного мессенджера согласие не открывает канал. Проверить применимость статьи 15 закона № 41-ФЗ, в том числе категорию владельца агрегатора. Не считать даже уведомительный redirect-бот автоматически допустимым при таком запрете. Результат оценки хранить с областью и сроком проверки. [S15]

## 7. Серверная модель доказательств

**EVID-01.** Расширить существующие согласия и privacy-service. Для каждого события хранить: внутренний субъект или анонимная сессия; цель; `granted/denied/revoked`; область; ID и версия документа; полный неизменяемый текст либо надёжная ссылка на его неизменяемый архив; SHA-256; время сервера UTC; канал; ID предъявления; безопасный ID взаимодействия; версию реестра получателей; ссылку на предшествующее решение. Отдельно хранить основание для операций, не зависящих от согласия.

**EVID-02.** Полный текст нельзя заменять только хешем или ссылкой на постоянно редактируемую страницу. Подтверждённые версии не редактировать задним числом. При изменении цели, данных, круга получателей или существенных условий требуется оценка необходимости нового согласия. Исправление опечатки не должно автоматически сбрасывать всех пользователей; решение о совместимости версий регистрируется.

**EVID-03.** Журнал решений — добавляемый, текущее состояние — проекция с монотонной ревизией. Операция атомарно проверяет полномочия и версию, погашает предъявленный токен, записывает решение, обновляет ревизию и аудит. Ограничения БД не должны запрещать законное повторное согласие после отзыва или разрешать несколько конкурирующих текущих состояний.

**EVID-04.** Предъявление действительно 24 часа по проектному умолчанию; срок настраивается в утверждённой политике. Отзыв инвалидирует ранее выданные предложения в затронутой области. Для нового согласия требуется свежее предъявление. Транспортные часы и порядок доставки Telegram не являются порядком решений; источник порядка — транзакция БД.

**EVID-05.** Получение решения, просмотр, экспорт и отзыв защищены проверкой субъекта. Для web — CSRF-защита, безопасные сессионные cookie и ограничения повторов. Для бота — проверка акторов из BOT-03/04. IDOR, произвольный `targetUserId`, доверие переданному с клиента `recipient_id` и подмена цели недопустимы.

**EVID-06.** Хеши, серверные подписи журналов и контроль целостности являются защитой доказательств, а не электронной подписью клиента. Интерфейс не утверждает проверку паспортной личности, когда подтверждён только контроль сессии или Telegram-аккаунта.

**EVID-07.** Предусмотреть выгрузку пакета доказательств: показанный документ, область, событие подтверждения/отзыва, цепочка версий и сведения о способе аутентификации. Доступ — только собственнику данных или уполномоченному сотруднику с аудитом; не публиковать архивы в GitHub и не отправлять их в открытый чат.

## 8. Допуск внешней обработки и гонки отзыва

**EGRESS-01.** Встроить единый механизм допуска в существующие API/application/worker. Перед постановкой задания и повторно непосредственно перед отправкой проверить: основание; действующую область согласия, если оно нужно; статус получателя; разрешённые поля; режим канала; версию политики; отсутствие блокирования/удаления. Проверка в одном web-экране недостаточна.

**EGRESS-02.** Передавать только разрешённую схему полей. Структуры пользователя и полная история не сериализуются целиком. Нельзя сохранять неизвестные поля «для совместимости». Нормализация и локальное выявление запрещённых данных дополняют контроль схемы, но не доказывают абсолютное обезличивание произвольного текста.

**EGRESS-03.** Отзыв атомарно увеличивает ревизию разрешений и отменяет ещё не отправленные зависимые задания. Диспетчер использует проверяемый барьер ревизии, а не долгоживущий кэш `granted`. Гонка «проверка → отзыв → отправка» покрывается интеграционным тестом и документированной точкой начала отправки.

**EGRESS-04.** Уже начатый сетевой запрос нельзя считать отозванным задним числом. Такие операции получают состояние `in_flight_at_revocation` или эквивалентное существующее состояние, прекращаются при технической возможности и включаются в процедуру удаления у получателя. Поздний ответ не попадает автоматически клиенту, эксперту, в профиль или повторную обработку, если допуск утрачен. Финансовые факты и неизвестный исход сверяются без дальнейшего использования содержания.

**EGRESS-05.** Повторный запуск worker, webhook-дубликат и retry не обходят проверку. Нельзя освобождать финансовый резерв или объявлять операцию неисполненной только потому, что персональный payload удаляется. При несовместимости срока хранения с действующим recovery-контрактом маршрут не активируется до согласования безопасного восстановления.

**EGRESS-06.** Успешный клик клиента не включает провайдера. Итоговое разрешение — пересечение допуска функции, правового основания, пользовательской области и готовности конкретной интеграции. При отсутствии любого обязательного условия выполнять только разрешённый локальный сценарий. Не предлагать ложный AI-ответ как результат реально выполненного запроса.

**EGRESS-07.** Не добавлять отдельный privacy-прокси, если те же проверки можно разместить в существующей транспортной границе. Реестр и guards используют текущие B1/B2/B3-механизмы. Live-флаги и финансовые лимиты не ослабляются; ручной `enabled=true` без доказательств не должен проходить стартовую проверку.

**VENDOR-01.** Реестр получателей содержит юридическое лицо, роль, страны и площадки обработки, upstream-поставщиков, доступ поддержки, категории данных, цели, срок хранения каждого вида копии, обучение, удаление, контакт по инцидентам и подтверждающие документы. Статусы: неизвестно, проверяется, допущено в указанной области, заблокировано. Одного российского ИНН или домена недостаточно.

**VENDOR-02.** Для FirstVDS получить сведения по основному серверу, снимкам, резервному хранилищу, дополнительному object storage, администрированию, мониторингу и средствам защиты трафика. Закрепить разграничение обязанностей. Учитывать реальную конфигурацию услуги, а не общее рекламное описание хостинга. [S16]

**VENDOR-03.** Selarti сохранить при подтверждённой допустимой схеме. До live-обработки получить договорные условия для клиентских данных Тони, фактическую цепочку LLM-провайдеров, сведения о журналах/истории/копиях и возможности прекращения. Требуемый режим проекта: минимизация запросов, отсутствие самостоятельного использования для обучения и ненужной долговременной истории. Это требования к поставщику, не утверждение, что Selarti уже их поддерживает.

**VENDOR-04.** Если маршрут включает трансграничную передачу, предварительно собрать предусмотренные законом сведения и пройти отдельную процедуру уведомления. Для соответствующих стран учесть десятидневный рабочий срок рассмотрения, приостановления и решения РКН. Система не должна превращать истечение таймера в безусловное разрешение. Статус допуска утверждается по документам. [S05]

**VENDOR-05.** Разделение локализованного сбора и последующей передачи допустимо рассматривать при оценке архитектуры. Письмо Минцифры от 12.05.2025 № П25-44929 является разъяснением, а не индивидуальным разрешением. Оно не подтверждает схему «временная запись в Москве, постоянная клиентская база за рубежом». Нужны согласованные хранение и обновление копий, а также фактический договор провайдера. [S07]

**VENDOR-06.** Для разрешения такого маршрута одновременно обновить внутреннее решение о запрете передач, реестр обработки, уведомления, публичную политику и нужные версии согласий. Сначала документы и испытание на синтетических данных, затем отдельная активация. При отказе провайдера раскрывать цепочку блокируется эта интеграция; весь проект не переписывается автоматически.

**VENDOR-07.** Google Sheets и Make не получают клиентскую базу, сообщения, контакты, отзывы с идентификаторами или персональные выгрузки. Сохранить принятый запрет их использования как PII-хранилищ. Допустимость агрегированных проекций проверяется на возможность выделить человека; UUID и редкое сочетание характеристик не являются достаточным обезличиванием. CI, GitHub, задачи и внешние инструменты разработки также не получают production-дампы и клиентские примеры.

**VENDOR-08.** Planerka получает только согласованный календарный минимум после проверки цепочки. Название события не содержит диагноза, проблемы клиента и контактных данных. Идентификатор брони не объявляется анонимным только из-за непрозрачного формата. Передача эксперту и поставщику календаря — разные получатели и проверяются раздельно.

**VENDOR-09.** Внешние генераторы персонажа, анимации и озвучки могут использовать утверждённые вымышленные материалы без данных клиентов. Не отправлять фото, голосовые сообщения, лица или истории клиентов для «улучшения персонажа». Права на исходники, голос, изображения и допустимость использования результата проверяются перед публикацией. Голос и фото не объявлять автоматически биометрией: значение имеет фактическое использование для установления личности; отдельно проверить статью 11 при таком сценарии.

## 10. Чувствительные данные, специалисты и несовершеннолетние

**SENS-01.** В выбранном one-click-релизе не активировать сценарии целевого сбора диагнозов, лечения, интимной жизни и других специальных категорий без самостоятельного подтверждённого основания. Когда основание — согласие, обычная кнопка не выполняет требование письменной формы. Электронное подписание такого документа в данный релиз не входит. [S02]

**SENS-02.** Локальная обработка, RAM-only, удаление после ответа, шифрование и слово «справочный» не являются самостоятельными исключениями. Убрать такие обоснования из A005 и связанных сценариев. Если бизнес-функция прямо предполагает обсуждение здоровья, её нельзя отметить выполненной только установкой DLP-фильтра. Она остаётся заблокированной до отдельного решения.

**SENS-03.** Для случайно присланных запрещённых сведений реализовать минимальный локальный обработчик: не пересылать поставщику; не сохранять исходное сообщение, цитату, подробное резюме или медицинскую метку в аудит; вернуть нейтральное ограничение и разрешённый путь связи. Процедуру получения и удаления утвердить юридически. Фильтр не гарантирует, что первоначальной обработки не было, и не разрешает систематический сбор под видом случайных сообщений.

**SENS-04.** Базовая беседа ограничивается организационным подбором. Не каждое упоминание настроения, йоги или предпочтения автоматически признавать диагнозом/религией; классифицировать по содержанию и назначению. Однако обходные формулировки «не диагноз, а состояние» не должны пропускать тот же медицинский смысл. Промпт и каталог не провоцируют заполнение медицинской анкеты.

**SENS-05.** Передача эксперту: показать названного получателя, бронь и конкретные передаваемые поля. Нельзя отправлять полный диалог или заметку всем специалистам. Сохранить проверку `expert_handoff` в чтении кабинета и отправке; отзыв скрывает необязательные сведения и запускает уведомление о прекращении у получателя. Связь отзыва `expert_note` и `expert_handoff` согласовать с действующим контрактом проекта, не обходить его отдельным API.

**SENS-06.** Если эксперт получает только минимальные данные для исполнения выбранной клиентом услуги, основание и роли определить явно. «Клиент», слот и ссылка на встречу не объявляются автоматически обезличенными. Отказ от необязательной заметки не отменяет оплаченную услугу; невозможность допустимого обслуживания передаётся в существующий процесс переноса/возврата.

**SENS-07.** Публичная карточка эксперта и отзыв клиента получают отдельную проверку публикации и, где требуется, согласие на распространение с предпросмотром и ограничениями по полям. Отзыв в приватной поддержке не становится публичным материалом по умолчанию. [S13]

**SENS-08.** Сохранить принятую модель 18+ без паспортной анкеты для обычного согласия. Возрастная декларация — самостоятельный продуктовый факт, не доказательство документальной проверки. При достоверном обнаружении несовершеннолетнего зависимые взрослые сценарии приостанавливаются; запросы по данным, безопасности и уже существующим обязательствам не исчезают. Не создавать автоматическую долговременную демографию по Telegram-профилю.

## 11. Аналитика, cookies и технические журналы

**TRACK-01.** Устранить немедленную загрузку Метрики из `apps/web/index.html`, включая `noscript`-пиксель. Не устанавливать необязательные cookies и не отправлять аналитические запросы до соответствующего выбора. Для базового запуска аналитика может оставаться полностью выключенной — это не требует дополнительного согласия на первом экране. [R05]

**TRACK-02.** На согласиях, входе, чате, в кабинете, записях и формах с персональными сведениями не загружать Webvisor и сторонние инструменты записи страницы. На публичном лендинге разрешать только утверждённую минимальную аналитику после отдельного выбора. Маскирование полей не подменяет этот проектный запрет. [S21]

**TRACK-03.** Отдельно закрыть SPA-переход: уже загруженный на лендинге скрипт не должен наблюдать приватный экран. Предпочтительный минимальный способ — вход в приватную часть через чистый first-party bootstrap/перезагрузку без аналитического тега с переиспользованием модулей приложения. Альтернатива допускается только при доказуемом прекращении записи и отсутствии утечек. Простого запрета новых `hit` недостаточно.

**TRACK-04.** Удалить персональные данные и секреты из адресов, query string, referrer, dataLayer, breadcrumbs и crash report. Проверить сторонние шрифты, captcha, CDN, виджеты записи и embedded-календари. Исключения проходят реестр получателей. Сбор технических security-событий и маркетинговые события имеют разные основания и наборы полей.

**TRACK-05.** Логи API, nginx, worker и приложения используют allow-list безопасных полей: метод, нормализованный шаблон маршрута, код состояния, код ошибки, длительность, безопасная корреляция. Запрещены body, текст диалога, raw update, Authorization, cookies, webhook secrets и значения `botKey`. При этом не уничтожать всю диагностику: наличие безопасных кодов ошибок и статусов проверяется тестами.

**TRACK-06.** Отзыв аналитики прекращает новые обращения и удаляет доступные необязательные first-party идентификаторы; обработка у получателя учитывается в общей процедуре прекращения. Не заявлять, что очистка browser cookie равна уничтожению всей истории у поставщика.

Указать клиенту, какие данные остаются и почему; отзыв не удаляет платёжные обязательства автоматически.

**RIGHTS-05.** Расширить существующее задание удаления на профиль, контактные связи, необязательные заметки, файлы, индексы, embeddings, кэши, очереди, разрешённые копии и получателей. Не подменять удаление сменой display name либо HMAC от user ID. Остаточные учётные факты отделяются, получают собственное основание и срок.

**RIGHTS-06.** Удаление у обработчиков подтверждать доступными договорными/API-доказательствами; у самостоятельных операторов учитывать их роль и законные обязанности. Недоступность API Telegram или обязательное хранение платёжного оператора нельзя обозначать как выполненное уничтожение. Статус пользователя должен различать удалено у нас, запрос направлен, подтверждение ожидается, сохранено на отдельном основании.

**RIGHTS-07.** Состояния `processor_complete` и `backup_verified` либо их расширение выставляются только по доказательствам. Отсутствие ответа поставщика — не положительный receipt. Автоматизированное уничтожение сопровождать актом и выгрузкой журнала по требованиям приказа РКН № 179; электронное оформление не создаёт бумажную обязанность для клиента. [R04, S14]

**RIGHTS-08.** Выдача копии данных — из защищённого российского кабинета после проверки пользователя. Не отправлять архив с профилем и историей обычным вложением в Telegram. Временная ссылка на загрузку имеет короткий срок, проверку владельца и защиту от попадания в referrer/аналитику. Отзыв конкретного согласия и удаление аккаунта — разные операции; удаление требует отдельного понятного подтверждения.

## 13. Сроки хранения и резервные копии

**RET-01.** До активации утвердить единую машиночитаемую политику сроков. Каждая категория получает основание, начало отсчёта, срок, ответственного и обработчик очистки. Ни налоговое хранение, ни трёхлетняя исковая давность не дают автоматического основания сохранять любую переписку или весь профиль.

Ниже — предлагаемые проектные пределы, а не универсальные сроки закона. Они заменяют конфликтующие настройки только после утверждения изменения DEC-PLT-004/PLT-012.

| Категория | Предлагаемое правило |
| --- | --- |
| Текст до необходимого согласия; запрещённые анкеты | Не сохранять в постоянное хранилище; не использовать повторно |
| Предъявление consent-кнопки | Срок действия 24 часа; минимальный след отказов/ошибок — до 30 дней при обоснованной необходимости |
| Обычный необязательный профиль | Не более 24 месяцев неактивности; раньше — при прекращении цели/отзыве |
| Контекст в outbox для разрешённого запроса | Удалять после терминального исхода в пределах 24 часов; неясные исходы — отдельный recovery-предел, предварительно согласованный с протоколом |
| Recovery-предел текста | Предлагаемый технический потолок 7 суток; без утверждённого конечного значения маршрут запрещён |
| Минимальные access-логи | До 7 суток; security-события — до 90 суток, без содержимого диалогов |
| Доказательства согласий | Предлагается до 3 лет после прекращения соответствующей обработки, с отдельным обоснованием и минимизацией |
| Счета, чеки, обязательные договорные записи | По реестру конкретных норм и категории документа; не единые «5 лет на всё» |
| Объектные и файловые копии | Срок исходной категории, не независимое бессрочное хранение |
| Резервные копии | Предлагаемая ротация до 30 календарных дней; законный срок конкретного уничтожения имеет приоритет |

**RET-02.** Не допускать молчаливое бесконечное продление срока из-за retry, нового бэкапа, активности другого члена семьи или безрезультатного обращения worker. Обязательные финансовые факты сверки должны сохраняться без исходного пользовательского текста, где это возможно. Несовместимость минимального recovery и установленного срока является блокирующим дефектом интеграции.

**RET-03.** Для более короткого применимого срока уничтожения предусмотреть выборочное удаление, проверяемое уничтожение ключей при подходящей архитектуре либо иной юридически подтверждённый способ. Обычная ротация не отменяет обязанность. Исключительный порядок блокирования при невозможности своевременного уничтожения по части 6 статьи 21 применяется только документированно, а не как штатная шестимесячная отсрочка для всех. [S09]

**RET-04.** Журнал отзыва и удаления переживает восстановление основной БД. До открытия восстановленного сервера для пользователей и внешних вызовов применяются актуальные удаления, блокировки и ревизии согласий. Изоляция restore-площадки, проверка очищенных данных и запрет внешней отправки входят в обязательный учебный сценарий.

**RET-05.** Не хранить доказательства бессрочно под видом append-only. Неизменяемость означает запрет подделки истории в пределах законного срока, а не вечное хранение. Подлежащие сохранению акты уничтожения и журнал оформляются с предусмотренными для них сроками; сам процесс уничтожения не должен пересоздавать полный профиль клиента.

## 14. Защита сервера и реагирование

**SEC-01.** Выполнить инвентаризацию ИСПДн, модель угроз и определение уровня защищённости; оформить требуемые меры по статье 19 и ПП РФ № 1119. Не объявлять УЗ-2, необходимость определённого сертификата или достаточность стандартного VPS без оценки. Подтверждение региона и подтверждение защищённости — разные доказательства. [S11, S12]

**SEC-02.** Сохранить существующую схему развёртывания. PostgreSQL не публиковать в интернет; разделить роли приложения, worker, миграций и администратора. Применить минимальные права, защищённый административный доступ и многофакторную защиту для администраторов. Разработчик не получает доступ к данным клиентов по умолчанию.

**SEC-03.** Использовать TLS, защищённое хранение секретов, ротацию ключей, обновления ОС и зависимостей, ограничение исходящих адресов и аудит привилегированных действий. Резервные копии шифровать, ключи хранить отдельно с проверяемым восстановлением. `.env`, токены, дампы, реальные переписки и клиентские consent-пакеты не включать в Git, CI-артефакты, промпты внешних помощников и отчёты разработчиков.

**SEC-04.** При отказе реестра, БД или проверки разрешения прекращать соответствующие внешние отправки, не переходя на режим «разрешить для доступности». При этом health endpoint, безопасная диагностика, публичные документы и обработка обращений по доступным каналам должны сохраняться, где это технически возможно.

**SEC-05.** Назначить ответственного за инциденты и резервного исполнителя. Для инцидента, подпадающего под часть 3.1 статьи 21, регламент учитывает уведомления РКН за 24 часа и за 72 часа, оба срока — от выявления. Автоматические таймеры формируют задачи и эскалации, но не отправляют непроверенные юридические сообщения самостоятельно. [S09]

**SEC-06.** Провести учебные сценарии: утечка токена бота; ошибочная отправка данных поставщику; компрометация кабинета эксперта; недоступность провайдера при запросе удаления; восстановление БД после отзыва. Доказательства учений не содержат персональных данных клиентов. Аварийное отключение не стирает журнал инцидента и финансовые факты.

## 15. Публичные документы, платежи и статус бизнеса

**LEGAL-01.** Утвердить актуальные реквизиты оператора и контакт для обращений. Обновить уведомление РКН об обработке либо подтвердить применимое исключение; трансграничное уведомление вести отдельно. Внутренние утверждения и доступный государственный электронный документооборот не требуют от клиента распечатывать согласия. [S10, S16]

**LEGAL-02.** Обновить политику, отдельные согласия, оферту, правила cookies, перечень обработчиков, сроки, контакты и порядок реализации прав. Удалить формулировки «начало диалога означает согласие», «cookies не являются персональными данными» и категоричное «передачи за рубеж отсутствуют», если разрешённый маршрут этому не соответствует. Сайт и бот получают документы из одного версионируемого источника.

**LEGAL-03.** До live-работы Telegram оформить проверку фактического статуса Тони и ограничений мессенджеров. До запуска персонализированных рекомендаций проверить применимость требований статьи 10.2-2 закона № 149-ФЗ и, при необходимости, опубликовать предусмотренную информацию. Проверка касается фактических функций, а не выбранного маркетингового названия. [S15, S19]

**LEGAL-04.** В акте допуска указать дату применяемой редакции законодательства. На дату данного ТЗ, 21 сентября 2026 года, изменения по законам № 289-ФЗ и № 290-ФЗ с 1 октября 2026 года ещё не вступили в силу. Для релиза после этой даты провести отдельную оценку применимости регулирования платформ и связанных обязанностей. Не переносить допуск автоматически через эту контрольную дату. [S24, S25]

**PAY-01.** Использовать существующий серверный контур ЮKassa. Платёжные реквизиты карты вводятся у платёжного поставщика в выбранном сценарии; Тоня хранит только допустимые идентификаторы и учётные факты. Возврат браузера на сайт не подтверждает оплату: использовать проверенное серверное состояние и действующие механизмы сверки. [S20]

**PAY-02.** Не класть здоровье, историю клиента и ненужные контакты в metadata, описание, return URL и логи. При этом обязательные реквизиты чека и реальный предмет расчёта не искажать ради «обезличивания». Договор с платёжным провайдером, фискализация, возвраты, рекуррентные списания при наличии и роль посредника проверяются отдельно оператором и бухгалтерией; согласие на данные не открывает `PAYMENTS_ENABLED`.

**PAY-03.** Не превращать отзыв согласия в автоматическую отмену оплаченной услуги, списание остатка или утрату права на возврат. При невозможности продолжать конкретный канал предоставить законный канал исполнения либо провести существующий процесс урегулирования. Изменение финансовых правил в данное ТЗ не входит.

**LEGAL-05.** Клинические обещания, лицензируемые услуги, рекламные размещения и платное продвижение специалистов проходят отдельную проверку применимости. Пока модель не подтверждена, соответствующая функция не объявляется закрытой общим дисклеймером. Базовый consent-релиз не является разрешением на новую медицинскую, рекламную или платёжную бизнес-модель.

## 16. Миграция существующих пользователей

**MIG-01.** Выполнить инвентаризацию старых решений, документов и потоков. Классифицировать: доказуемое действующее согласие; необходимая договорная обработка; недостаточные доказательства; запрещённая либо избыточная обработка. Нельзя проставить всем пользователям новую версию согласия или датировать новые события задним числом.

**MIG-02.** Старые записи сохраняются как история с признаком проверенной/неподтверждённой достаточности. Для необязательной обработки без основания положительное состояние не наследуется. При следующем обращении показывается актуальный отдельный документ. Одно нажатие создаёт новое, перспективное решение, а не легализует прежние действия.

**MIG-03.** Принятое ранее 60-дневное окно можно использовать только для организационной кампании. Оно не разрешает продолжать обработку, у которой нет основания, и не удлиняет законный срок уничтожения. Сервисное уведомление не превращать в рекламную рассылку. Молчание не считается новым согласием и не требует записи вымышленного пользовательского отказа.

**MIG-04.** Уже оплаченные права, остатки, брони и необходимые учётные факты сохраняются на соответствующем основании. «Grandfathering» не распространяется автоматически на необязательный профиль, рекламу, чувствительные сведения и новые передачи. Снятие неподтверждённого публичного отзыва и прекращение неправомерной обработки не откладываются только до завершения кампании.

**MIG-05.** Миграция допускает dry run на обезличенном наборе, контрольные суммы учётных агрегатов до/после и отчёт о классифицированных строках. Реальные данные не переносятся в Claw/CI или GitHub ради проверки. Подготовка миграции не является разрешением исполнять её на production.

## 18. Обязательная матрица приёмки

Все тесты выполняются на синтетических либо специально подготовленных неперсональных данных. Указанные сценарии являются минимальным набором; покрытие не ограничивается только позитивным нажатием кнопки.

| ID | Проверка | Ожидаемый результат |
| --- | --- | --- |
| T01 | Новый клиент открывает обычное согласие на сайте | Отдельный документ, одна кнопка; нет SMS, паспорта, обязательной дополнительной галочки |
| T02 | Клиент закрывает окно или отказывает | `granted` отсутствует, необязательная функция не работает, каталог и права доступны |
| T03 | Пользователь даёт согласие в личном боте | Решение связано с точным документом и действительным актором |
| T04 | `/start`, оплата либо первое сообщение без согласия | Согласие не создаётся; AI не вызывается |
| T05 | БД недоступна при нажатии | Нет ложного успеха и внешней отправки |
| T06 | Двойной клик и дубликат webhook | Одно логическое решение, нет двойного списания/бронирования |
| T07 | Устаревшая версия документа | Старое нажатие не принимается за согласие с новым текстом |
| T08 | Изменён архив принятого текста | Нарушение целостности обнаруживается; документ нельзя молча заменить |
| T09 | Callback другого человека/из группы/с другого бота | Отказ без раскрытия данных |
| T10 | Поддельный webhook и просроченный токен | Решение не записывается |
| T11 | Права получены только через подставленный `targetUserId` | Экспорт, просмотр и отзыв чужих данных запрещены |
| T12 | Отзыв на сайте и поздний старый callback в Telegram | Согласие не восстанавливается |
| T13 | Новое явное согласие после отзыва | Только свежее предъявление и новая ревизия создают разрешение |
| T14 | Сайт и бот не связаны доказуемо | Согласия не объединяются по `username` или имени |
| T15 | Нажата базовая кнопка | Маркетинг, публикация и другие независимые цели не активируются |
| T16 | Согласие AI есть, документы провайдера не допущены | Отправка блокируется; локальный fallback не маскируется под внешний ответ |
| T17 | Допущенный провайдер получает неизвестное поле | Схема отвергает запрос до отправки |
| T18 | Отзыв между enqueue и dispatch | Задание не отправляется |
