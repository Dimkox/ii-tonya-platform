## 1. БЛОК А: РАЗДЕЛЕННЫЙ ФЛОУ ПРОДАЖ (TARIFF & PROMOTION)
**Статус:** 🔴 КРИТИЧНО / BLOCKER

**Главное правило:**
1.  Сначала мы продаем **ценность эксперта** и фиксируем **базовую цену**.
2.  Только после того, как клиент принял базовую цену (или отработали возражения), мы предлагаем **акцию** как бонус за быстрое решение.
3.  Это два разных сообщения. Между ними может быть диалог.

### 1.1. Изменение полей в БД (`residents_applications`)

| Поле | Тип | Описание | Логика заполнения |
| :--- | :--- | :--- | :--- |
| `base_tariff_amount` | DECIMAL | Персональный тариф без скидок | Заполняется при первом успешном расчете (`calculate_base_price`). |
| `base_offer_shown_at` | DATETIME | Время показа базовой цены | Триггер для начала работы скрипта "Отработка возражений". |
| `promo_accepted_flag` | BOOLEAN | Согласен ли клиент на акцию? | DEFAULT FALSE. Становится TRUE только если клиент явно выбирает пакет со скидкой. |
| `final_locked_price` | DECIMAL | Итоговая цена к оплате | NULL до оплаты онбординга. Заполняется суммой из шага акции или базой, если акции нет. |
| `offer_expiry_date` | DATE | Дата окончания текущего предложения | Рассчитывается динамически на основе графика скидки (см. п. 1.3). |

### 1.2. Алгоритм диалога (Step-by-Step Flow)

#### Шаг 1: Генерация Базового Предложения
*   **Триггер:** Завершение квалификации (ответы на вопросы о нише/городе).
*   **Действие системы:**
    1.  Вызывает `calculate_base_price()`. Применяются модификаторы города/формата. Скидки акции НЕ применяются.
    2.  Сохраняет результат в `base_tariff_amount`.
    3.  Ставит `base_offer_shown_at = now()`.
*   **Сообщение бота (Промпт "Продажа ценности"):**
    > *«{Имя}, спасибо за информацию!*
    > *На основе вашего опыта и региона, ваш персональный тариф размещения составит **{Base_Price} ₽/мес**.*
    > *Эта цена включает приоритетный подбор клиентов и автоматизацию записей.*
    > *Как вам такие условия? Есть ли вопросы по стоимости?»*
*   **Логика:** Бот ждет ответа. Если есть возражения — включается скрипт обработки возражений (уже прописан в демо-боте). Цель этапа — получить согласие на базовую модель сотрудничества.

#### Шаг 2: Презентация Акции «Энергия начала»
*   **Триггер:** Клиент ответил положительно на базовый тариф («Да», «Ок», «Готов») или исчерпал возражения.
*   **Действие системы:**
    1.  Проверяет текущую дату относительно `base_offer_shown_at`.
    2.  Определяет этап скидки ($S$) и доступность пакета (см. таблицу ниже).
    3.  Рассчитывает цену акции: $P_{promo} = Base\_Price \times (1 - S)$.
*   **Сообщение бота (Промпт "Upsell Акция"):**
    > *«Отлично! Я рад, что мы нашли подход.*
    > *Сейчас у нас действует закрытая акция **«Энергия начала»** для первых участников.*
    > *Если вы оплатите взнос за онбординг сегодня, я зафиксирую для вас цену **{Promo_Price} ₽/мес** вместо {Base_Price} ₽.*
    > *Это экономия {Discount_Amount} ₽ каждый месяц!*
    > *Предложение действует до [{Expiry_Date}] включительно.*
    > *Готовы воспользоваться этим шансом и зафиксировать цену?»*
    > *[Кнопка: Да, хочу по акции]* *[Кнопка: Нет, оставьте базовую цену]*

#### Шаг 3: Фиксация и Оплата Онбординга
*   **Вариант А: Клиент выбрал акцию.**
    1.  Система берет `Promo_Price`.
    2.  Генерирует ссылку на оплату **Онбординга (3000 ₽)**.
    3.  В тексте сообщения указывает: *«Оплата взноса 3000 ₽ фиксирует вашу цену {Promo_Price} ₽ навсегда.»*
*   **Вариант Б: Клиент отказался от акции.**
    1.  Система берет `Base_Price`.
    2.  Генерирует ссылку на оплату **Онбординга (3000 ₽)**.
    3.  Текст: *«Ваша цена зафиксирована на уровне {Base_Price} ₽.»*
*   **Webhook Success (Оплата 3000 ₽):**
    1.  Берется сумма из выбранного варианта (A или B).
    2.  Записывается в поле `final_locked_price`.
    3.  Статус -> `ONBOARDING_STARTED`.
    4.  Открывается доступ к рабочему боту.

### 1.3. График Сроков Действия (Expiration Logic)

Ссылка на оплату онбординга и фиксация цены действуют строго по графику акции, привязанному к дате `base_offer_shown_at`.

| Дней прошло с момента базового расчета | Скидка (%) | Срок действия этого предложения | Сообщение при истечении срока |
| :--- | :--- | :--- | :--- |
| **0–3 дня** | 40% (+15% пакет) | До конца 3-го дня | *«Скидка 40% истекла. Теперь доступна скидка 30%. Новая цена: ...»* |
| **4–6 дней** | 30% (+10% пакет) | До конца 6-го дня | *«Скидка 30% истекла. Доступна скидка 20%. Новая цена: ...»* |
| **7–9 дней** | 20% | До конца 9-го дня | *«Акция завершена. Цена возвращается к базовой: {Base_Price} ₽.»* |
| **10+ дней** | 0% | Постоянно | *«Период акции окончен. Ваш тариф: {Base_Price} ₽.»* |

**Важно:** При каждом изменении этапа (переходе с 3-го на 4-й день и т.д.) система должна:
1.  Аннулировать старую ссылку на оплату онбординга (если она еще не оплачена).
2.  Сгенерировать новую ссылку с новой ценой фиксации.
3.  Отправить уведомление клиенту: *«⏳ Внимание! Срок действия вашей скидки истекает через [X] часов. Чтобы зафиксировать цену [Old_Price], оплатите сейчас. После этого цена станет [New_Price].»*

### 1.4. Чек-лист приемки
- [ ] Бот никогда не показывает цену акции одновременно с базовой.
- [ ] Поле `base_offer_shown_at` заполняется только один раз.
- [ ] При переходе между этапами скидки старые ссылки блокируются, новые генерируются автоматически.
- [ ] Если клиент молчит 10 дней, ему предлагается только базовая цена.

## 2. БЛОК Б: ОПТИМИЗИРОВАННЫЙ ДРАЙВЕР ХЭШТЕГОВ (TOKEN SAVER)
**Статус:** ⚙️ ВАЖНО / PERFORMANCE

**Проблема:** Использование LLM для каждого тега дорого и медленно.
**Решение:** Гибридный поиск (Regex + Pre-computed Embeddings).

### 2.1. Архитектура модуля (`hashtag_recommender_fast.py`)

1.  **Pre-processing (One-time setup):**
    *   При старте сервиса или обновлении базы тегов, для каждого тега и его синонимов из `hashtags_db` рассчитываются векторы эмбеддингов (используя легкую модель типа `all-MiniLM-L6-v2` или аналог, кэшируемые локально).
    *   Результат сохраняется в отдельную таблицу `tag_embeddings_cache` или файл `.bin`.
2.  **Runtime Logic (Per Resident):**
    *   **Шаг 1: Keyword Extraction (Cheap).**
        *   Из текста услуги выделяются существительные и глаголы (без использования тяжелого LLM API). Используется библиотека `Natasha` или `PyMorphy2`.
        *   Список ключевых слов ($K_w$).
    *   **Шаг 2: Exact Match (Fastest).**
        *   Поиск точных совпадений слов из $K_w$ с полями `tag_value` и массивами синонимов в БД.
        *   Найденные теги добавляются в список кандидатов с весом 100.
    *   **Шаг 3: Semantic Similarity (Medium Cost).**
        *   Для слов из $K_w$, не нашедших точного совпадения, берем их эмбеддинги.
        *   Сравниваем с кэшированными эмбеддингами тегов (Cosine Similarity).
        *   Порог схожести > 0.85 -> Теги добавляются в кандидаты с весом 50.
    *   **Шаг 4: Ranking & Limit.**
        *   Сортировка кандидатов по весу.
        *   Ограничение вывода: Максимум 15 тегов.
        *   Никаких вызовов GPT/Claude API в реальном времени. Только локальные вычисления.

### 2.2. Чек-лист приемки
- [ ] Время генерации списка тегов < 500 мс.
- [ ] Отсутствие обращений к платным LLM API в процессе подбора тегов.
- [ ] Тег находится даже если пользователь написал синоним (например, "ПА" вместо "панические атаки").

## 3. БЛОК В: ДИНАМИЧЕСКИЙ ГЕНЕРАТОР СЛОТОВ (SERVICE-BASED)
**Статус:** ⚙️ ВАЖНО / FEATURE

**Логика:** Слоты создаются под конкретную услугу, учитывая её длительность и буфер.

### 3.1. Алгоритм (`slot_scheduler_v2.py`)

1.  **Входные данные:**
    *   Список активных услуг резидента (`service_items` where `is_active=True`).
    *   Параметры расписания (`schedule_rules`: дни, часы, перерывы, default_buffer).
2.  **Процесс генерации (для каждого рабочего дня месяца):**
    *   Инициализировать курсор времени `current_time = start_time`.
    *   Цикл `while current_time < end_time`:
        *   Проверить, попадает ли интервал `[current_time, current_time + duration]` в перерывы. Если да -> сдвинуть курсор на конец перерыва.
        *   Для каждой услуги в списке:
            *   Рассчитать слот: `{start: current_time, end: current_time + service.duration}`.
            *   Добавить буфер: `next_cursor = end + buffer_time`.
            *   Создать запись в `available_slots` с привязкой к `service_id`.
        *   Обновить `current_time = next_cursor`.
3.  **Ручной импорт (CSV/Text):**
    *   Парсер принимает формат: `YYYY-MM-DD HH:MM-HH:MM ServiceName`.
    *   Валидация:
        *   Проверка на пересечение с уже занятыми слотами (`status != FREE`).
        *   Проверка существования `ServiceName` в каталоге резидента.
    *   Если ошибок нет -> Batch Insert в БД.

### 3.2. Чек-лист приемки
- [ ] Консультация 60 мин и Диагностика 90 мин создают разные по длине слоты.
- [ ] Буфер применяется корректно между разными услугами.
- [ ] Ручной импорт не создает конфликтов с авто-генерацией.
