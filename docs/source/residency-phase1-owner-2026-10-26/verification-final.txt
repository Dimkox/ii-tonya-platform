# 📋 ТЗ ДЛЯ GETZILLA: ФИНАЛЬНАЯ ВЕРСИЯ МОДУЛЯ ВЕРИФИКАЦИИ (PHASE 1)
## Модуль: `verification_system` | Статус: УТВЕРЖДЕНО К РАЗРАБОТКЕ

**Контекст:**
Система первичного отбора кандидатов. Жесткое разделение процессов «Верификация» и «Расчет тарифа».
**Важное уточнение по бизнес-модели:**
Платформа **НЕ принимает платежи от клиентов за услуги экспертов**. Эксперты работают напрямую с клиентами. Платформа выступает только как навигатор. Если эксперт предоставляет ссылку на оплату, бот может её переслать, но ответственность за транзакцию лежит на эксперте.
Налоговый статус запрашивается исключительно для оценки серьезности намерений резидента (триггер доверия), а не для юридических обязательств перед платформой. Физлица без статуса допускаются при наличии других подтверждений компетентности (соцсети, отзывы).

## 2. БИЗНЕС-ЛОГИКА ФОРМЫ (DYNAMIC FORM ENGINE)

Бот ведет диалог, меняя вопросы в зависимости от выбранной `role_type`.

### Шаг 1. Выбор роли и категории
*   **Input:** Inline Buttons для выбора ролей.
*   **Logic:**
    *   Если роль `ESOTERIC` или `OTHER`: Скрыть обязательный запрос дипломов. Заменить на поле "Описание пути/кейсов".
    *   Показать инфо-блок с критериями BASIC vs EXCLUSIVE. Пользователь выбирает цель (`BOTH` разрешено).

### Шаг 2. Сбор данных (Conditional Fields)

#### Общие поля для всех:
1.  **Tax Status:** Выбор из списка. *Подсказка:* "Это помогает нам оценить масштаб вашего бизнеса. Отсутствие ИП/Самозанятости не является причиной отказа, если есть другие доказательства экспертизы."
2.  **Location:** Город / Онлайн.
3.  **Social Links:** Telegram, VK, Instagram, Website. (Приоритет: наличие живых подписчиков и отзывов).
4.  **Motivation:** Открытый текст. "Чего вы ждете от проекта? Почему именно вы?"

#### Специфика по ролям:
*   **🧠 EXPERT:**
    *   Ниша и методы.
    *   Опыт (лет).
    *   Документы: Дипломы/Сертификаты (если есть). Для эзотериков — ссылки на отзывы/медиа.
    *   Кейсы: Текстовое описание результатов клиентов.
*   **🏢 CENTER:**
    *   Тип помещения, вместимость.
    *   Документы: Договор аренды/собственности (скан).
    *   Фото/Видео тура (обязательно).
    *   Инфраструктура (чекбоксы).
*   **🎪 ORGANIZER:**
    *   Описание формата мероприятия.
    *   Программа и спикеры.
    *   Кейсы прошлых ивентов (фото/видео/отзывы).
*   **🎓 EDU_PROJECT:**
    *   Название школы/курса.
    *   Лицензия (если есть) или аккредитация.
    *   Преподавательский состав.
    *   Отзывы выпускников.

### Шаг 3. Опция "Загрузка брифа" (Fallback Logic)
*   **Feature:** Кнопка "У меня есть резюме/презентация".
*   **Action:** При загрузке PDF/DOCX:
    1.  Сохранить файл в S3.
    2.  Вызвать функцию `parse_document_to_form(file_id)`.
    3.  LLM извлекает данные -> заполняет пустые поля формы автоматически.
    4.  Бот показывает предзаполненные поля и спрашивает: *"Я извлек эти данные. Верно ли? Что нужно исправить?"*
    5.  **Error Handling:** Если парсинг не удался (плохой скан, рукописный текст) -> Бот пишет: *«Не удалось прочитать файл автоматически. Пожалуйста, ответьте на стандартные вопросы вручную.»* и переходит к обычному флоу.

## 3. АВТОМАТИЧЕСКИЕ ПРОВЕРКИ (BACKGROUND JOBS)

После сабмита формы запускается Celery Task `run_auto_verification(application_id)`.

### 3.1. OCR & Document Check (`doc_verifier.py`)
*   **Tool:** Tesseract + PyMuPDF.
*   **Logic:**
    1.  Распознать текст с картинок дипломов/сертификатов.
    2.  Найти ключевые слова: название ВУЗа, специальность, год.
    3.  Сравнить со значением поля `specialization_claimed` в форме.
    4.  **Output:** Записать в `system_check_result`:
        ```json
        {
          "docs_verified": true/false/null, // null если документов нет
          "mismatch_warning": "Заявлен как Психолог, в дипломе Педагог",
          "license_required_flag": true // Только если ниша медицинская
        }
        ```

### 3.2. Social Media Health Check (`social_parser.py`)
*   **Tools:** Telethon (TG), VK API, Instagrapi/scraping.
*   **Logic:**
    1.  Пройтись по списку `social_links`.
    2.  Получить дату последнего поста.
    3.  Если > 30 дней -> Флаг `INACTIVE_PROFILE`.
    4.  Взять последние 5 постов. Проверить наличие медиа и комментариев.
    5.  **Output:** Записать в `system_check_result`:
        ```json
        {
          "social_health": "GOOD" | "MODERATE" | "BAD",
          "last_post_date": "2026-10-20",
          "has_live_engagement": true/false
        }
        ```
    *   **Примечание:** Это вспомогательная информация для менеджера. Окончательное решение о "человечности" профиля принимает человек.

## 4. ИНТЕРФЕЙС МЕНЕДЖЕРА (ADMIN PANEL / BOT COMMANDS)

Менеджер получает уведомление и карточку решения.

### Карточка заявки (Message Format):
```text
🆕 ЗАЯВКА #[SHORT_ID]: [NAME]
Роль: [ROLE_TYPE] | Категория: [TARGET_CATEGORY]
Налоги: [TAX_STATUS] | Локация: [CITY]

🤖 СИСТЕМНАЯ ПРОВЕРКА:
✅ Docs: [MATCH/MISMATCH/N/A]
⚠️ Socials: [ACTIVE/INACTIVE] (Last post: [DATE])
💰 Avg Check: [AMOUNT] RUB (если указано)

🔗 ССЫЛКИ ДЛЯ РУЧНОЙ ПРОВЕРКИ:
[TG Profile] [VK Page] [Docs Folder]

📝 МОТИВАЦИЯ:
"[TRUNCATED_TEXT...]"

✅ CHECKLIST МЕНЕДЖЕРА:
1. Перейти по ссылкам. Оценить визуал, тон, наличие живых отзывов.
2. Сверить документы с заявленной нишей.
3. Определить итоговую категорию.
4. Принять решение.

ДЕЙСТВИЯ:
[✅ ОДОБРИТЬ БАЗОВЫЙ]
[⭐ ОДОБРИТЬ ЭКСКЛЮЗИВ]
[🔄 ЗАПРОСИТЬ ДОПОЛНИТЕЛЬНО]
[❌ ОТКАЗАТЬ]
```

### Логика кнопок действий:
1.  **[ОДОБРИТЬ]:**
    *   Меняет статус заявки на `APPROVED_BASIC` или `APPROVED_EXCLUSIVE`.
    *   Триггерит событие `on_application_approved(user_id, category)`.
    *   **ВАЖНО:** НЕ отправляет сообщение пользователю сразу! Только пишет в БД. Следующее действие инициируется отдельным скриптом приветствия (см. п.5).
2.  **[ЗАПРОСИТЬ ДОПОЛНИТЕЛЬНО]:**
    *   Открывает модальное окно для ввода конкретных вопросов.
    *   Меняет статус на `INFO_REQUESTED`.
    *   Запускает таймер 48 часов.
    *   Отправляет пользователю шаблон сообщения с вопросами.
3.  **[ОТКАЗАТЬ]:**
    *   Требует выбора причины из dropdown (внутренне): `LOW_QUALITY_SOCIALS`, `NO_DOCUMENTS_AND_CASES`, `NICHE_MISMATCH`, `BLACKLIST`.
    *   Меняет статус на `REJECTED`.
    *   Отправляет пользователю вежливый шаблон отказа (без раскрытия внутренней причины).

## 5. ПОЛЬЗОВАТЕЛЬСКИЙ ФЛОУ (POST-DECISION ACTIONS)

### Сценарий: Одобрение
Как только менеджер жмет "Одобрить":
1.  Система обновляет профиль пользователя: `is_resident_candidate = True`.
2.  Бот отправляет пользователю **ТОЛЬКО** результат верификации:
    > *«{Name}, поздравляем! ✅ Вы прошли верификацию. Ваш статус резидента подтвержден.*
    > *Чтобы продолжить, нажмите кнопку ниже для расчета вашего персонального тарифа.»*
    > *[Кнопка: Рассчитать тариф]*
3.  **НЕ ВЫСТАВЛЯТЬ СЧЕТ.** НЕ ГОВОРИТЬ ЦЕНУ.
4.  При нажатии кнопки -> Переход в существующий сценарий `tariff_calculation_flow` (уже реализован в демо-боте). Там бот задаст вопросы про локацию/чек и выдаст цену.

### Сценарий: Запрос допов
1.  Пользователь получает вопросы.
2.  Отвечает текстом/файлами.
3.  Система сохраняет ответы в `application_updates`.
4.  После получения всех ответов -> Повторный запуск `run_auto_verification` -> Новая карточка менеджеру.

### Сценарий: Отказ
Шаблон сообщения:
> *«{Имя}, спасибо за ваше время и интерес к проекту ии-Тоня.*
> *Мы внимательно изучили вашу заявку. На данном этапе мы формируем базу из специалистов, чья экспертиза и формат работы полностью соответствуют нашим текущим внутренним стандартам качества и потребностям нашей аудитории.*
> *Ваше предложение пока не прошло этот фильтр. Это не оценка вашей личности или профессионализма, а вопрос соответствия специфике нашего сервиса сейчас.*
> *Мы сохранили ваши контакты. Если наши критерии изменятся, мы свяжемся с вами первыми.*
> *Желаем процветания вашей практике! 🙏»*

## 6. ТЕХНИЧЕСКИЕ ТРЕБОВАНИЯ И ОПТИМИЗАЦИЯ

1.  **Локальный парсинг:** Использовать Python библиотеки для чтения файлов. Не гонять большие объемы текста через платные LLM API без необходимости. LLM использовать только для структурирования сырого текста из PDF в JSON форму.
2.  **Кэширование соцсетей:** Результаты проверки соцсетей кэшировать на 24 часа. Не делать повторные запросы к VK/TG API каждый раз при открытии карточки менеджером.
3.  **Безопасность:** Все ссылки на документы хранить в приватном бакете S3. Генерировать временные presigned URLs для менеджера.
4.  **Логирование:** Каждое действие менеджера (одобрение/отказ) должно логироваться с timestamp и ID менеджера для аудита.

## 7. ЧЕК-ЛИСТ ПРИЕМКИ (ACCEPTANCE CRITERIA)

- [ ] Форма собирает данные динамически в зависимости от роли.
- [ ] Налоговый режим запрашивается у всех, но не является жестким блокером.
- [ ] Загрузка PDF-брифа распознается и заполняет поля. При ошибке парсинга — graceful fallback на ручную форму.
- [ ] Авто-проверка дипломов дает флаг MATCH/MISMATCH.
- [ ] Авто-проверка соцсетей определяет активность (>30 дней = INACTIVE).
- [ ] Менеджер видит кликабельную карточку со ссылками.
- [ ] Кнопка "Одобрить" НЕ вызывает расчет цены напрямую, а переводит в следующий этап диалога (кнопка "Рассчитать тариф").
- [ ] Отказ формируется корректно, без обвинений в "нехватке информации" (сначала запрос, потом отказ).
- [ ] Миграции БД проходят успешно на staging среде.
