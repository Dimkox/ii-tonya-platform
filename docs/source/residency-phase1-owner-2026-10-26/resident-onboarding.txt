# 📋 ТЗ ДЛЯ GETZILLA: МОДУЛЬ ОНБОРДИНГА И ПОДДЕРЖКИ РЕЗИДЕНТА (PHASE 1)
## Модуль: `resident_onboarding_engine` | Статус: УТВЕРЖДЕНО К РАЗРАБОТКЕ

**Контекст:**
Реализация глубокого сбора данных о резиденте после оплаты взноса (3000 ₽). Система должна поддерживать три режима ввода (Загрузка файлов, Чек-лист для внешнего ИИ, Пошаговое интервью), автоматически генерировать слоты на основе графика работы, интегрировать геолокацию Яндекс.Карт и управлять жизненным циклом карточки от черновика до активной публикации.

**Важное бизнес-правило:**
Карточка попадает в базу знаний (`PUBLISHED_IN_DB`) сразу после модерации менеджером, но **НЕ становится видимой клиентам** (`ACTIVE_VISIBLE`) до момента подтверждения анонсов и оплаты основного тарифа. Клиенты видят эксперта только по релевантному запросу.

## 2. ЛОГИКА СБОРА ДАННЫХ (INPUT MODES)

Бот предлагает пользователю выбрать режим. Реализовать три отдельных флоу, которые сходятся в один объект `DraftProfile`.

### Режим А: Парсинг внешних источников (File/URL)
1.  **Upload:** Пользователь присылает PDF/DOCX или ссылку на сайт.
2.  **Extraction:**
    *   Локальный парсер (`PyMuPDF`, `BeautifulSoup`) извлекает текст.
    *   LLM-промпт: *«Извлеки следующие данные из текста и верни JSON: full_name, specialization, bio_summary, services_list (array of objects with title, price, duration, description), social_links, location_address.»*
3.  **Gap Analysis:** Сравнение полученного JSON с Master Template. Определение пустых полей.
4.  **Interactive Fill:** Бот задает вопросы ТОЛЬКО по пустым полям.
5.  **Fallback:** Если парсинг не удался (ошибка OCR/Low Quality) -> Переход в Режим В (Пошаговое интервью) с сообщением: *«Не удалось прочитать файл автоматически. Давайте пройдемся по вопросам вручную.»*

### Режим Б: Внешний чек-лист (Template Download)
1.  **Delivery:** Бот отправляет `.docx` / `.md` шаблон со структурой Master Template.
2.  **Return:** Пользователь присылает заполненный файл.
3.  **Validation:** Аналогично Режиму А (Parcing -> Extraction -> Gap Analysis -> Interactive Fill).

### Режим В: Пошаговое интервью (Guided Flow)
1.  **Sequential Questions:** Бот ведет диалог блок за блоком.
2.  **Context Awareness:**
    *   Если ответ на формат = `ONLINE`, пропустить блок адреса.
    *   Если ответ на формат = `OFFLINE`, запросить адрес и инструкции.
    *   Если ответ на онлайн-формат = `UNDECIDED`, блокировать кнопку «Отправить на проверку» до выбора варианта.
3.  **Detail Push:** Алгоритм проверки длины ответа. Если `< 50 символов` для блока `bio` или `description`, бот запрашивает уточнения: *«Расскажите подробнее...»*

## 3. АВТОМАТИЧЕСКИЕ ПРОВЕРКИ И ГЕНЕРАЦИЯ (BACKGROUND JOBS)

После завершения ввода данных запускается Celery Task `process_resident_draft(resident_id)`.

### 3.1. AI Guardrails (Auto-Moderation)
Перед отправкой менеджеру система проверяет текстовые поля (`bio`, `services.description`) на:
1.  **Forbidden Words:** Список стоп-слов (гарантии лечения, «излечу рак», «быстрые деньги», агрессия).
2.  **Spam Detection:** Повторы слов, случайный набор символов.
3.  **Completeness Check:** Наличие цен, длительностей, контактов.
*   **Result:** Если найдены критические ошибки -> Статус `AUTO_CHECK_FAILED`. Бот просит пользователя исправить конкретные пункты. Если ошибок нет -> Статус `MANAGER_REVIEW`.

### 3.2. Geolocation Service Integration
Если `format` включает `OFFLINE`:
1.  Взять поле `location_address`.
2.  Вызвать Yandex Maps API (`geocode`).
3.  Получить координаты `(lat, lon)`.
4.  Сформировать публичную ссылку: `https://yandex.ru/maps/?pt={lon},{lat}&z=17&l=map`.
5.  Сохранить в `yandex_maps_url`.

### 3.3. Slot Generator Algorithm
На основе таблицы `schedule_rules`:
1.  Цикл по дням месяца (или выбранному периоду).
2.  Для каждого рабочего дня:
    *   Создать интервалы от `start_time` до `end_time` с шагом `default_session_duration + buffer_time_minutes`.
    *   Исключить интервалы, пересекающиеся с массивом `breaks_json`.
3.  Записать полученные даты/времена в таблицу `available_slots` со статусом `FREE`.
4.  Отправить пользователю превью списка слотов для подтверждения или ручной корректировки (удаление лишних, добавление специальных).

### 3.4. Hashtag Recommendation Engine
1.  Анализ текста `services.description` и `bio`.
2.  Поиск совпадений с базой `hashtags_taxonomy` (TF-IDF или Embedding similarity).
3.  Формирование топ-20 рекомендуемых тегов.
4.  Предложение пользователю выбрать галочками + поле для ввода `custom_tags`.
5.  Объединение выбранных системных и пользовательских тегов в поле `tags_array`.

## 4. ИНТЕРФЕЙС МЕНЕДЖЕРА (ADMIN PANEL / KANBAN)

Менеджер видит карточку в колонке **«Финальная модерация»**.

### Карточка заявки (UI Elements):
*   **Header:** Имя, Специализация, Город.
*   **Tabs:**
    1.  **Профиль:** Био, Фото (галерея), Контакты.
    2.  **Услуги:** Список `service_items` с ценами, описаниями, тегами.
    3.  **Логистика:** Адрес + Карта (интерактивная), Онлайн-формат.
    4.  **Расписание:** Календарь сгенерированных слотов.
*   **System Flags:** Результаты Auto-Moderation (Green/Red).
*   **Actions:**
    *   [✅ Одобрить размещение] -> Меняет статус профиля на `APPROVED_IN_DB`. Отправляет уведомление резиденту.
    *   [❌ На доработку] -> Требует ввода комментария. Возвращает статус `DRAFT` или `AUTO_CHECK_FAILED` с указанием причин.
    *   [✏️ Редактировать] -> Доступ только для суперадмина или при наличии прав. Изменения логируются.

## 5. ЖИЗНЕННЫЙ ЦИКЛ СТАТУСОВ (STATE MACHINE)

```mermaid
stateDiagram-v2
    [*] --> DRAFT: Оплата онбординга (3000₽)
    DRAFT --> AUTO_CHECK_FAILED: Ошибки в тексте/данных
    AUTO_CHECK_FAILED --> DRAFT: Исправлено пользователем
    DRAFT --> MANAGER_REVIEW: Auto-check passed
    MANAGER_REVIEW --> APPROVED_IN_DB: Менеджер одобрил
    MANAGER_REVIEW --> DRAFT: Менеджер вернул на доработку

    APPROVED_IN_DB --> PROMO_CONFIRMED: Пользователь подтвердил анонсы
    APPROVED_IN_DB --> SUSPENDED: Нет анонсов > 7 дней (Эскалация)

    PROMO_CONFIRMED --> AWAITING_PAYMENT: Генерация счета на тариф
    AWAITING_PAYMENT --> ACTIVE_VISIBLE: Оплата ЮKassa Success
    AWAITING_PAYMENT --> SUSPENDED: Не оплачено > 3 дней

    ACTIVE_VISIBLE --> ARCHIVED: Пауза / Непродление
    ACTIVE_VISIBLE --> SUSPENDED: Много отказов / Нарушения
```

**Примечание:** Только в состоянии `ACTIVE_VISIBLE` профиль индексируется в поисковом движке для клиентов.

## 6. МЕХАНИКА ОБНОВЛЕНИЙ (ONGOING MAINTENANCE)

### Триггеры:
Кнопки в боте эксперта: «Добавить услугу», «Обновить слоты», «Изменить профиль».

### Процесс обновления услуги/профиля:
1.  Пользователь вносит изменения -> Создается запись в `service_items` или `residents_profiles` со статусом `version_status = PENDING_UPDATE`.
2.  Запускается `process_resident_draft` (Auto-check).
3.  Если успех -> Уведомление менеджеру в Kanban (колонка «Обновления»).
4.  Менеджер смотрит Diff (что изменилось).
5.  [✅ Опубликовать] -> `version_status` меняется на `LIVE`. Старая версия архивируется.
6.  [❌ Отклонить] -> Комментарий пользователю.

### Процесс обновления слотов:
1.  Пользователь меняет график или добавляет ручные слоты.
2.  Система пересчитывает `available_slots`.
3.  Конфликтующие с уже забронированными (`BOOKED_*`) слоты игнорируются.
4.  Обновление происходит мгновенно без модерации менеджера (техническая операция), но логируется.
5.  **Command:** «Убери слот [дата/время]» -> Статус слота меняется на `BOOKED_EXTERNAL`.

### Мониторинг качества (Cron Job):
*   Раз в сутки рассчитывать `% Cancelled_Bronies_by_Resident` за последний месяц.
*   Если `> 20%` -> Отправить алерт менеджеру: *«Резидент [Имя] часто отменяет брони. Проверить расписание.»*

> *«🎉 Поздравляем! Вы стали активным резидентом ии-Тони!*
>
> *Ваша карточка теперь доступна для подбора клиентам. Вы будете получать уведомления о новых заявках прямо здесь.*
>
> **Как работать с заявками:**
> • Подтверждайте, отменяйте или переносите встречи кнопками в уведомлении.

>
> **Обновление информации:**

> Частые отмены могут привести к приостановке рекомендаций. Давайте будем уважать время наших клиентов!»*

## 8. ЧЕК-ЛИСТ ПРИЕМКИ (ACCEPTANCE CRITERIA)

- [ ] Реализованы 3 режима ввода данных (File, Checklist, Interview).
- [ ] Fallback на интервью при ошибке парсинга работает корректно.
- [ ] Блок онлайн-формата блокирует финализацию, если выбран `UNDECIDED`.
- [ ] Геолокация генерирует рабочую ссылку Яндекс.Карт для офлайн-адресов.
- [ ] Алгоритм генерации слотов учитывает перерывы, буферы и длительность сессий.
- [ ] Хэштеги рекомендуются на основе семантики текста + есть поле для своих тегов.
- [ ] Auto-moderation ловит запрещенные слова и возвращает ошибку пользователю.
- [ ] Менеджер видит полный дифф и может утвердить/отклонить обновление.
- [ ] Статус `ACTIVE_VISIBLE` устанавливается ТОЛЬКО после успешного вебхука от ЮKassa об оплате основного тарифа.
- [ ] Cron job мониторинга отказов запускается ежедневно и шлет алерты при превышении порога.
- [ ] Команда «Убери слот» мгновенно меняет статус слота на `BOOKED_EXTERNAL`.
