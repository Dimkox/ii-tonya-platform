# 📋 ТЗ ДЛЯ GETZILLA: СТАБИЛИЗАЦИЯ ФУНДАМЕНТА (PRE-PHASE 1)
## Модуль: `core_stabilization` | Статус: КРИТИЧНО / СРОЧНО

**Контекст:**
Перед началом внедрения крупных модулей «Верификация» и «Онбординг», необходимо устранить технические риски в текущем коде, которые могут привести к падению сервиса или логическим ошибкам при интеграции новых флоу. Эти задачи блокируют стабильную работу будущих сценариев.

**Цель:** Подготовить чистую, устойчивую архитектуру для подключения динамических форм, парсинга файлов и генерации слотов.

## 1. ЗАДАЧА А: ИЗОЛЯЦИЯ ЛОГИКИ АКТИВАЦИИ РАБОЧЕГО КАБИНЕТА

**Проблема:**
В текущей реализации промо-бота (`@ii_tonya_expert_promo_bot`) отсутствует четкий интерфейс для перевода пользователя в рабочий бот (`@ii_tonya_expert_bot`). Риск смешивания бизнес-логики продаж и операционных функций в одном файле/хэндлере.

**Требование:**
Вынести функцию активации доступа в отдельный сервисный слой (Service Layer), не зависящий от конкретного типа бота.

### Реализация:
1.  Создать метод `activate_resident_workspace(user_id: int)` в классе `ResidencyService`.
2.  **Логика метода:**
    *   Проверка наличия записи в таблице `residents_profiles` со статусом `APPROVED_IN_DB` или выше.
    *   Если запись есть -> Обновить флаг `has_access_to_work_bot = True` в профиле пользователя.
    *   Отправить push-уведомление пользователю через Promo-bot API: *«Доступ открыт! Перейдите в рабочий кабинет: [t.me/ii_tonya_expert_bot]»*.
    *   Залогировать событие `ACCESS_ACTIVATED` в таблицу `audit_logs`.
3.  **Интеграция:**
    *   Вызывать этот метод ТОЛЬКО после успешного вебхука оплаты Онбординга (3000 ₽) ИЛИ после одобрения менеджером на этапе Верификации (если оплата еще не прошла, но доступ нужен для заполнения анкеты).
    *   *Важно:* Не вызывать автоматически при регистрации. Только по триггеру события.

## 2. ЗАДАЧА Б: ОБРАБОТКА ОШИБОК ПАРСИНГА (GRACEFUL FALLBACK)

**Проблема:**
Библиотеки чтения PDF/DOCX (`PyMuPDF`, `python-docx`) могут выбрасывать исключения при работе с поврежденными файлами, сканами без текстового слоя или неподдерживаемыми форматами. Это приведет к краху воркера Celery и потере данных пользователя.

**Требование:**
Реализовать надежную обертку для всех операций извлечения текста.

### Реализация:
1.  Создать утилиту `SafeDocumentParser.parse(file_path_or_bytes) -> dict | None`.
2.  Внутри обернуть вызовы библиотек в блок `try-except`:
    ```python
    try:
        # Попытка чтения PDF
        doc = fitz.open(stream=file_data, filetype="pdf")
        text = "".join([page.get_text() for page in doc])
        
        if len(text.strip()) < 50: # Слишком короткий текст, вероятно пустой скан
             raise ValueError("InsufficientTextContent")
             
        return {"source": "pdf", "content": text}
        
    except Exception as e:
        logger.warning(f"Parsing failed for user {user_id}: {str(e)}")
        return None # Возвращаем None вместо падения
    ```
3.  **Логика бота (Handler):**
    *   Если `SafeDocumentParser` вернул `None`:
        *   Бот отправляет сообщение: *«Не удалось автоматически прочитать файл. Возможно, это картинка или сложный формат. Давайте заполним данные вручную.»*
        *   Автоматически переключает сессию пользователя в режим **Интервью (Scenario B/C)**.
    *   Никаких ошибок 500 на стороне клиента.
