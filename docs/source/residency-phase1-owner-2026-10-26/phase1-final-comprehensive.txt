# 📋 ФИНАЛЬНОЕ ТЕХНИЧЕСКОЕ ЗАДАНИЕ (PHASE 1)
## Проект «ии-Тоня» | Полный цикл: Стабилизация, Продажи, Онбординг, Поддержка

**Для:** ИИ-агента разработчика / Технического лида платформы `ii-tonya-platform`
**Статус:** УТВЕРЖДЕН. Приоритеты зафиксированы окончательно.
**Цель:** Реализовать сквозной, максимально автоматизированный процесс от входа эксперта в воронку до активации его карточки и регулярных обновлений.
**Главный принцип:** **Автоматизация рутины + Человеческий контроль качества.**
*   Система делает всё техническое: генерирует коды, считает рефералов, выставляет счета через ЮKassa, собирает данные, отправляет уведомления, фильтрует спам.
*   Менеджер делает только то, что нельзя доверить машине: верификация личности/компетенций, утверждение контента карточки, ответы на нестандартные эскалации.

>

Твоя задача — **дополнить и связать** эти модули с новой бизнес-логикой оплаты и верификации, а не переписывать их с нуля. Если найдешь конфликт логики — используй команду `@conflict_alert`.
> 2.  **Не жди отмашки на каждый шаг.** Выполняй задачи строго по порядку блоков Этапа 0 -> Этап 1 (Блок А -> Блок Б -> Блок В -> Блок Г). Как только этап завершен и протестирован локально — коммить в Git и двигайся к следующему блоку. Заказчик будет проверять статусы выборочно или по запросу `@status_report`.
> 3.  **Заглушки вместо ожидания (Anti-Blocker Policy).** Если для реализации конкретного пункта (например, текст анкеты верификации или скрипт онбординга) нет точных данных от заказчика — создавай техническую заглушку (`TODO: Wait for Content Spec`), сохраняя структуру БД и API endpoints. **Не блокируй работу всего потока из-за отсутствия текстов.** Мы пришлем контент позже, ты просто подставишь его в готовые слоты.
> 4.  **Терминология (Строго!).**
>     *   Для экспертов: **«Бонусы»** (реферальные начисления). Переменная в коде: `bonus_points`.
>     *   Для клиентов: **«Купоны»** (внутренняя валюта сервиса). Переменная в коде: `coupons_balance`.
>     *   Не путай эти понятия ни в коде, ни в ответах бота.
> 5.  **Сроки выполнения задач:** Максимально быстрые. Параллельная работа допускается **только внутри одного блока**, если задачи независимы. Переход к следующему блоку возможен только после закрытия критических зависимостей предыдущего.
> 6.  **Взаимодействие с заказчиком.** Ты должен сам мониторить репозиторий и выявлять пробелы. Если информации не хватает для продолжения архитектуры — ставь заглушку и сообщай об этом через `@request_spec`, но не останавливайся.

## 3. ЭТАП 1: CORE PHASE 1 — ЦИКЛ СТАНОВЛЕНИЯ РЕЗИДЕНТОМ
*Задача: Выстроить сквозной процесс от регистрации до публикации карточки.*

### Блок А: Лидогенерация, Разделенные Продажи и Фиксация Тарифа (Promo-Bot)
*(Интегрируется с уже существующими скриптами воронки)*

#### P1.A1. Ref Code & Tracking
*   Генерация уникального `ref_code` при первом `/start`.
*   Отслеживание новых регистраций по коду (парсинг deep-link `?start=CODE`).
*   Счетчик уникальных TG IDs. Сохранение связи `referrer_id -> new_user_id` в БД.

#### P1.A2. Auto-PDF Reward
*   Триггер: `COUNT(referrals) >= 2 AND pdf_sent == false`.
*   Действие: Отправить PDF-гайд (файл предоставлен заказчиком отдельно).
*   Установить флаг `pdf_sent = true`.
*   Начислить бонусы в поле `bonus_points` со статусом `FROZEN`.

#### P1.A3. Tariff Calculation & Locking (РАЗДЕЛЕННЫЙ ФЛОУ ПРОДАЖ)
**Главное правило:** Сначала продаем базовую цену. Только после согласия клиента предлагаем акцию. Два разных сообщения. Между ними может быть диалог.

1.  **Шаг 1: Генерация Базового Предложения.**
    *   Триггер: Завершение квалификации.
    *   Действие: Вызвать `calculate_base_price()`. Применить модификаторы (город, формат). Скидки акции НЕ применять.
    *   Сохранить результат в `base_tariff_amount`.
    *   Поставить `base_offer_shown_at = now()`.
    *   Сообщение бота (Промпт "Продажа ценности"): *«{Имя}, ваш персональный тариф составит {Base_Price} ₽/мес. Как вам такие условия?»*
    *   Логика: Ждать ответа. Обработка возражений (скрипт из демо-бота). Цель — получить согласие на базовую модель.

2.  **Шаг 2: Презентация Акции «Энергия начала».**
    *   Триггер: Клиент ответил положительно на базовый тариф.
    *   Действие: Проверить дату относительно `base_offer_shown_at`. Определить этап скидки ($S$). Рассчитать $P_{promo}$.
    *   Сообщение бота (Промпт "Upsell Акция"): *«Сейчас действует акция... Цена {Promo_Price} ₽ вместо {Base_Price} ₽. Предложение действует до [{Expiry_Date}]...»*
    *   Кнопки: [Да, хочу по акции] / [Нет, оставьте базовую].

3.  **Шаг 3: Фиксация и Оплата Онбординга.**
    *   Вариант А (Акція): Берем `Promo_Price`. Генерируем ссылку на оплату **Онбординга (3000 ₽)**. Текст: *«Оплата фиксирует вашу цену {Promo_Price} ₽ навсегда.»*
    *   Вариант Б (Базовая): Берем `Base_Price`. Генерируем ссылку на оплату **Онбординга (3000 ₽)**. Текст: *«Ваша цена зафиксирована на уровне {Base_Price} ₽.»*

4.  **Шаг 4: Обработка решений и истечения срока.**
    *   **Webhook Success (Оплата 3000 ₽):** Записать выбранную сумму в `final_locked_price`. Статус -> `ONBOARDING_STARTED`. Открыть доступ к рабочему боту.
    *   **Если клиент молчит:** Каждые сутки система проверяет статус. При переходе между этапами скидки (например, с 3-го на 4-й день):
        1.  Аннулировать старую ссылку.
        2.  Сгенерировать новую ссылку с новой ценой фиксации.
        3.  Отправить уведомление: *«⏳ Срок действия скидки истекает через [X] часов...»*
    *   **Просрочка > 10 дней:** Статус `STANDARD_TARIFF_LOCKED`. Цена фиксируется по базовой ставке. Повторные пересчеты запрещены. Снижение цены возможно только через реферальные бонусы.

#### P1.A4. Initiate Verification Request
*   После выбора тарифа бот формирует заявку на верификацию.
*   Статус пользователя меняется на `VERIFICATION_PENDING`.
*   Данные (ник, ниша, город, выбранный тариф, ссылка на анкету) отправляются в очередь менеджера.

### Блок Б: Верификация Претендента (Human-in-the-loop)
*Ключевой этап контроля качества. Автоматизируется только передача данных и уведомление результатов.*

#### P1.B1. Verification Queue Interface
*   Создание интерфейса (админка/бот-менеджер) для просмотра заявок со статусом `VERIFICATION_PENDING`.
*   Поля: Контактные данные, Анкета (текст/фото дипломов — *скрипт анкеты будет добавлен позже*), Расчетный тариф.
*   Динамическая форма сбора данных в зависимости от роли (`EXPERT`, `CENTER`, `ORGANIZER`, `EDU_PROJECT`, `ESOTERIC`, `OTHER`).
*   Опция загрузки готового брифа (PDF/Site) с парсингом и дозапросом недостающих полей.
*   Обязательный запрос налогового статуса (`tax_status`).

#### P1.B2. Manager Action: Approve/Reject
*   Кнопки [✅ Согласовано] / [❌ Отказано] / [🔄 Запросить инфо].
*   **При «Согласовано»:** Статус -> `APPROVED_FOR_PAYMENT`. Автоматическая генерация ссылки на оплату Онбординга (см. P1.A3 Шаг 3).
*   **При «Отказано»:** Выбор причины из шаблонов (`REJECT_NICHE_MISMATCH`, `REJECT_INSUFFICIENT_PROOF`, `REJECT_LEGAL_VIOLATION`). Отправка вежливого текста отказа.
*   **При «Запросить инфо»:** Шаблон `REQ_INFO_GENERIC`. Таймер 48 часов.

#### P1.B3. Onboarding Payment Webhook
*   Обработка успешной оплаты Онбординга (3000 ₽).
*   1. Статус -> `ONBOARDING_STARTED`.
*   2. Активация доступа к `@ii_tonya_expert_bot` (только в режиме интервью).
*   3. Запуск сценария сбора данных карточки (*скрипт вопросов будет добавлен позже*).

### Блок В: Онбординг Карточки и Публикация (Expert-Bot)
*Процесс наполнения базы знаний и подготовки резидента к работе.*

#### P1.C1. Data Collection Flow (Deep Dive)
*   Техническая возможность приема ответов пользователя (текст, фото, файлы) и сохранения их в промежуточную таблицу `card_drafts`.
*   **Блок 1 Профиль:** ФИО, Специализация, Био (детально), Фото (мин 3), Соцсети.
*   **Блок 2 Услуги:** Список услуг с названием, форматом, длительностью, ценой, описанием, показаниями, результатом, сроком действия (если есть), ссылкой на детали.
*   **Блок 3 Локация:** Адрес, инструкции как добраться, авто-генерация ссылки Яндекс.Карт.
*   **Блок 4 Онлайн:** Статичная ссылка на комнату (Dynamic пока заблокирован).
*   **Блок 5 Хэштеги:** Алгоритм рекомендации тегов на основе семантики текста услуги (см. ниже). Пользователь подтверждает выбор галочками + может добавить свои.
*   **Блок 6 Расписание:** Параметры рабочих дней, часов, перерывов, буфера. Авто-генерация слотов с учетом индивидуальной длительности каждой услуги. Или ручной импорт списка слотов.

#### P1.C2. AI Guardrails (Auto-Moderation)
*   Перед показом пользователю черновика, система проверяет текст на наличие стоп-слов и паттернов нарушений (медгарантии, фин. обещания, hate speech).
*   Если найдено нарушение Severity=`BLOCKER` -> Бот требует исправить текст.
*   Если найдено нарушение Severity=`WARNING` -> Карточка уходит менеджеру с флагом.

#### P1.C3. User Confirmation Loop

#### P1.C4. Manager Card Review Loop

*   Интерфейс: Просмотр собранной информации, возможность редактирования полей, кнопка [✅ Утвердить карточку].
*   *Заглушка:* Куда именно отправлять карточку менеджеру (отдельный чат/веб-интерфейс) — определить позже. Пока использовать стандартный механизм эскалации в поддержку.

#### P1.C5. Promo Materials Distribution
*   После утверждения карточки менеджером:
    1.  Система автоматически формирует пакет анонсов (тексты постов, баннеры) для рассылки резидентом по своим базам.
    *Примечание: Шаблоны материалов будут предоставлены заказчиком. Сейчас заглушка.*
    2.  Бот отправляет эти материалы пользователю с инструкцией.
    3.  Статус -> `AWAITING_PROMO_CONFIRMATION`.

#### P1.C6. Promo Confirmation Gate
*   Пользователь должен подтвердить факт публикации (загрузить скриншоты/ссылки).
*   Бот принимает медиа/ссылки.
*   Менеджер проверяет соответствие (опционально, можно автоматизировать распознавание ссылок позже).

#### P1.C7. Main Tariff Invoice Generation
*   Генерация счета на оплату основного тарифа резидентства (на выбранную сумму и период).
*   Отправка ссылки пользователю.

#### P1.C8. Activation on Success
*   Обработка успешной оплаты основного тарифа.
*   1. Статус -> `ACTIVE_RESIDENT`.
*   2. Карточка публикуется в боевой базе `experts_published`.
*   3. Разблокировка полного функционала в `@ii_tonya_expert_bot` (уведомления о бронях, баланс бонусов и т.д.).
*   4. Установка даты следующего платежа (`next_billing_date`).
*   5. Отправка финальной инструкции резиденту (как работать с заявками, как обновлять инфо, правила по слотам и отказам).

*   4. При дате возврата — автоматическое восстановление статуса `ACTIVE_RESIDENT` и возобновление показов.

## 4. СПЕЦИФИКАЦИЯ МОДУЛЕЙ (TECH DEEP DIVE)

### Модуль 1: Оптимизированный Драйвер Хэштегов (Token Saver)
**Проблема:** Использование LLM для каждого тега дорого и медленно.
**Решение:** Гибридный поиск (Regex + Pre-computed Embeddings).

1.  **Pre-processing (One-time setup):**
    *   При старте сервиса или обновлении базы тегов, для каждого тега и его синонимов из `hashtags_db` рассчитываются векторы эмбеддингов (легкая модель типа `all-MiniLM-L6-v2`, кэшируемые локально).
    *   Результат сохраняется в таблицу `tag_embeddings_cache`.
2.  **Runtime Logic (Per Resident):**
    *   **Шаг 1: Keyword Extraction (Cheap).** Извлечение ключевых слов из текста услуги через `Natasha`/`PyMorphy2`.
    *   **Шаг 2: Exact Match (Fastest).** Поиск точных совпадений с полями `tag_value` и массивами синонимов. Вес 100.
    *   **Шаг 3: Semantic Similarity (Medium Cost).** Сравнение эмбеддингов оставшихся слов с кэшем тегов (Cosine Similarity > 0.85). Вес 50.
    *   **Шаг 4: Ranking & Limit.** Топ-15 тегов. Никаких вызовов платных LLM API в реальном времени.

### Модуль 2: Динамический Генератор Слотов (Service-Based)
**Логика:** Слоты создаются под конкретную услугу, учитывая её длительность и буфер.

1.  **Авто-генерация:**
    *   Вход: Список активных услуг (`service_items`) и параметры расписания (`schedule_rules`).
    *   Цикл по рабочим дням: Курсор времени идет от `start_time` до `end_time`. Шаг = `service.duration` + `buffer`. Исключение перерывов.
    *   Результат: Массив объектов `{date, start_time, end_time, service_id}` в таблице `available_slots`.
2.  **Ручной импорт:**
    *   Парсер принимает формат: `YYYY-MM-DD HH:MM-HH:MM ServiceName` или CSV.
    *   Валидация на пересечения с занятыми слотами и существование услуги.
    *   Batch Insert в БД.

### Модуль 3: Контент Сейфти (Stop-Words Filter)
**Таблица `forbidden_patterns`:**
*   Regex паттерны для медгарантий, фин. обещаний, hate speech.
*   Severity: `BLOCKER` (не сохранить) / `WARNING` (сохранить, подсветить менеджеру).
*   Интеграция в процесс сохранения профиля и услуг. Логирование инцидентов в `security_logs`.

### Модуль 4: Коммуникационные Шаблоны (Refusal Scripts)
**Таблица `message_templates`:**
*   `REJECT_NICHE_MISMATCH`, `REJECT_INSUFFICIENT_PROOF` (повторная подача через 1 месяц), `REJECT_LEGAL_VIOLATION`, `REQ_INFO_GENERIC`, `REJECT_POST_PAYMENT_REFUND`.
*   UI менеджера позволяет выбирать шаблон, подставлять переменные `{NAME}`, `{QUESTION_X}` и редактировать перед отправкой.

## 7. ПРОТОКОЛ СВЯЗИ И КОНТРОЛЯ (COMMANDS FOR AGENT)

Чтобы мы не теряли нить управления, используй следующие протоколы связи. Это твой способ сигнализировать о прогрессе и проблемах.

### Команда: `@status_report`
*(Отправлять после завершения крупного блока или каждые 12 часов активной работы. Это заменяет ежедневные созвоны).*
```text
STATUS REPORT
Current Phase: [Например: Этап 1 - Блок Б]
Completed Tasks: [Список ID выполненных задач, напр. P1.B1, P1.B2]
In Progress: [Текущая активная задача, напр. P1.B3]
Blocked By: [Если есть блокировка: "Нет" или описание причины, напр. "Жду файл PDF"]
Next Steps: [Что планируешь делать следующим, напр. "Реализация webhook ЮKassa"]
Git Commit Hash: [Хеш последнего коммита в ветке разработки]
Conflicts Detected: [Yes/No. Если Yes — кратко опиши суть конфликта с кодом из п.1 инструкции]
```

### Команда: `@request_spec [Task_ID]`
*(Используй, если не хватает данных для технической реализации. Не останавливай работу, ставь заглушку и запрашивай спецификацию).*
**Пример:** `@request_spec P1.C3`
**Ответ агента (ожидается от тебя):** "Для задачи P1.C3 нужны шаблоны текстов анонсов и изображений баннеров. Ожидаю файлы."
Команда:  @module_ready [Module_Name]
(Когда модуль протестирован и готов к merge. Это сигнал для проверки качества).
Пример:  @module_ready Verification_Flow
Команда:  @conflict_alert
(Если обнаружено расхождение между новым планом и уже написанным кодом в репозитории. Это критически важно для сохранения целостности системы).
Пример:  @conflict_alert Logic in P1.A3 overrides existing tariff calculation script in promo_bot.py.
Разработчик, начинай с Этапа 0 (P0.1 - P0.5). Затем переходи к Этапу 1, Блок А. Держи фокус на связке Promo-Bot -> Separated Sales Flow -> Verification -> Payment. Тексты и скрипты интервью временно заменяй заглушками, чтобы не останавливать архитектуру.
