# 📋 ТЗ ДЛЯ GETZILLA: ПРОТОКОЛ ВЕРИФИКАЦИИ РЕЗИДЕНТОВ (PHASE 1)
## Модуль: `verification_system` | Статус: КРИТИЧНО

**Контекст:**
Мы внедряем систему первичного отбора кандидатов в проект «ии-Тоня». Это не просто форма, а сложный воркфлоу с динамическими полями, автоматической проверкой документов/соцсетей и передачей карточки менеджеру.
**Важно:** Этот модуль предшествует расчету тарифа. Сначала мы решаем «Пускаем или нет», потом — «Сколько стоит».

## 2. БИЗНЕС-ЛОГИКА ФОРМЫ (DYNAMIC FORM ENGINE)

Бот должен вести диалог, меняя вопросы в зависимости от выбранной `role_type`.

### Шаг 1. Выбор роли и категории
*   **Input:** Inline Buttons для выбора ролей (можно несколько, но основная одна).
*   **Logic:** Если выбрана роль `ESOTERIC` или `OTHER`, скрыть обязательный запрос дипломов, заменить на запрос "Описание пути/кейсов".
*   **Category Selection:** Показать инфо-блок с критериями BASIC vs EXCLUSIVE (тексты из ТЗ выше). Пользователь выбирает цель.

### Шаг 2. Сбор данных (Conditional Fields)
Реализовать движок условных полей. Примеры правил:

1.  **Если Role = CENTER:**
    *   Запросить: `property_proof_url` (скан договора аренды/собственности).
    *   Запросить: `capacity_int` (вместимость).
    *   Запросить: `amenities_list` (чекбокс: маты, кухня, парковка...).
2.  **Если Role = EXPERT:**
    *   Запросить: `education_docs` (если ниша требует лицензии — обязательно; если коучинг — опционально).
    *   Запросить: `average_check_rub` (для определения соответствия эксклюзиву >15k).
3.  **Для всех:**
    *   `tax_status` (Обязательно! Для будущих счетов).
    *   `social_links` (Telegram, VK, Instagram, Website).
    *   `motivation_text` (Open field).

### Шаг 3. Опция "Загрузка брифа"
*   **Feature:** Кнопка "У меня есть резюме/презентация".
*   **Action:** При загрузке PDF/DOCX:
    1.  Сохранить файл в S3/MinIO.
    2.  Вызвать функцию `parse_document_to_form(file_id)`.
    3.  LLM извлекает данные -> заполняет пустые поля формы автоматически.
    4.  Бот показывает предзаполненные поля и спрашивает: *"Я извлек эти данные. Верно ли? Что нужно исправить?"*
    5.  Пользователь корректирует -> Отправка.

## 3. АВТОМАТИЧЕСКИЕ ПРОВЕРКИ (BACKGROUND JOBS)

После сабмита формы запускается Celery Task `run_auto_verification(application_id)`.

### 3.1. OCR & Document Check (`doc_verifier.py`)
*   **Tool:** Tesseract + PyMuPDF.
*   **Logic:**
    1.  Распознать текст с картинок дипломов/сертификатов.
    2.  Найти ключевые слова: название ВУЗа, специальность, год.
    3.  Сравнить со значением поля `specialization_claimed` в форме.
    4.  **Output:** Записать в `system_check_result`:
        ```json
        {
          "docs_verified": true/false,
          "mismatch_warning": "Заявлен как Психолог, в дипломе Педагог",
          "license_required_flag": true // Если ниша медицинская
        }
        ```

### 3.2. Social Media Health Check (`social_parser.py`)
*   **Tools:** Telethon (TG), VK API (Community Token), Instagrapi (или scraping fallback).
*   **Logic:**
    1.  Пройтись по списку `social_links`.
    2.  Получить дату последнего поста.
    3.  Если > 30 дней -> Флаг `INACTIVE_PROFILE`.
    4.  Взять последние 5 постов. Проверить наличие медиа (фото/видео) и комментариев.
    5.  **Output:** Записать в `system_check_result`:
        ```json
        {
          "social_health": "GOOD" | "MODERATE" | "BAD",
          "last_post_date": "2026-10-20",
          "engagement_score": 0.8 // Условная метрика
        }
        ```

## 4. ИНТЕРФЕЙС МЕНЕДЖЕРА (ADMIN PANEL / BOT COMMANDS)

Менеджер должен получать уведомление и иметь возможность принять решение прямо в Telegram или через простую веб-админку.

### Вариант А: Управление через Telegram-бота Менеджера
Команда `/review_apps` выводит список заявок статуса `UNDER_REVIEW`.

**Карточка заявки (Message Format):**
```text
🆕 ЗАЯВКА #[SHORT_ID]: [NAME]
Роль: [ROLE_TYPE] | Категория: [TARGET_CATEGORY]
Налоги: [TAX_STATUS] | Локация: [CITY]

🤖 СИСТЕМНАЯ ПРОВЕРКА:
✅ Docs: [MATCH/MISMATCH/N/A]
⚠️ Socials: [ACTIVE/INACTIVE] (Last post: [DATE])
💰 Avg Check: [AMOUNT] RUB

🔗 ССЫЛКИ:
[TG Profile] [VK Page] [Docs Folder]

📝 МОТИВАЦИЯ:
"[TRUNCATED_TEXT...]"

ДЕЙСТВИЯ:
[✅ ОДОБРИТЬ БАЗОВЫЙ]
[⭐ ОДОБРИТЬ ЭКСКЛЮЗИВ]
[🔄 ЗАПРОСИТЬ ДОПОЛНИТЕЛЬНО]
[❌ ОТКАЗАТЬ]
```

### Логика кнопок действий:
1.  **[ОДОБРИТЬ]:**
    *   Меняет статус заявки на `APPROVED_BASIC` или `APPROVED_EXCLUSIVE`.
    *   Триггерит событие `on_application_approved(user_id, category)`.
    *   **ВАЖНО:** Не отправляет сообщение пользователю сразу! Только пишет в БД. Следующее действие инициируется отдельным скриптом приветствия (см. п.5).
2.  **[ЗАПРОСИТЬ ДОПОЛНИТЕЛЬНО]:**
    *   Открывает модальное окно (или серию сообщений) для ввода конкретных вопросов.
    *   Меняет статус на `INFO_REQUESTED`.
    *   Запускает таймер 48 часов.
    *   Отправляет пользователю шаблон сообщения с вопросами.
3.  **[ОТКАЗАТЬ]:**
    *   Требует выбора причины из dropdown (внутренне): `LOW_QUALITY_SOCIALS`, `NO_DOCUMENTS`, `NICHE_MISMATCH`, `BLACKLIST`.
    *   Меняет статус на `REJECTED`.
    *   Отправляет пользователю вежливый шаблон отказа (без раскрытия внутренней причины, кроме общих фраз).

## 5. ПОЛЬЗОВАТЕЛЬСКИЙ ФЛОУ (POST-DECISION ACTIONS)

### Сценарий: Одобрение
Как только менеджер жмет "Одобрить":
1.  Система обновляет профиль пользователя: `is_resident_candidate = True`.
2.  Бот отправляет пользователю **ТОЛЬКО** результат верификации:
    > *«{Name}, поздравляем! ✅ Вы прошли верификацию. Ваш статус резидента подтвержден.*
    > *Чтобы продолжить, нажмите кнопку ниже для расчета вашего персонального тарифа.»*
    > *[Кнопка: Рассчитать тариф]*
3.  **НЕ ВЫСТАВЛЯТЬ СЧЕТ.** НЕ ГОВОРИТЬ ЦЕНУ.
4.  При нажатии кнопки -> Переход в существующий сценарий `tariff_calculation_flow` (уже реализован в демо-боте). Там бот задаст вопросы про локацию/чек и выдаст цену.

### Сценарий: Запрос допов
1.  Пользователь получает вопросы.
2.  Отвечает текстом/файлами.
3.  Система сохраняет ответы в `application_updates`.
4.  После получения всех ответов -> Повторный запуск `run_auto_verification` -> Новая карточка менеджеру.

## 6. ТЕХНИЧЕСКИЕ ТРЕБОВАНИЯ И ОПТИМИЗАЦИЯ

1.  **Локальный парсинг:** Использовать Python библиотеки для чтения файлов. Не гонять большие объемы текста через платные LLM API без необходимости. LLM использовать только для структурирования сырого текста из PDF в JSON форму.
2.  **Кэширование соцсетей:** Результаты проверки соцсетей кэшировать на 24 часа. Не делать повторные запросы к VK/TG API каждый раз при открытии карточки менеджером.
3.  **Безопасность:** Все ссылки на документы хранить в приватном бакете S3. Генерировать временные presigned URLs для менеджера.
4.  **Логирование:** Каждое действие менеджера (одобрение/отказ) должно логироваться с timestamp и ID менеджера для аудита.
