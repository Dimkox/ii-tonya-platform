Status: design investigation only; no implementation or additional test authorization.

## Product selection and authority

Select by durable product evidence, not a request-provided purpose, amount, Telegram text or existence of merchant credentials.

- Existing composite/deferred intents always retain their original wave product. Recovery of an existing bound provider object uses fresh GET and its existing verifier, including after launch; creating a new wave payment remains subject to existing wave gates.
- A newly admitted public expert uses legacy onboarding invoices only when the authoritative launch configuration/time is public, the authenticated subject owns the invoice, the approved verification/form/selection is current and the invoice has no competing wave acquisition. This is `public_onboarding`; it does not manufacture a wave choice, grant or launch timestamp.
- A public main payment requires an existing legacy residency order and its immutable accepted quote/card authority, completed onboarding, correct authenticated owner, mode, amount and unexpired provider deadline. This is `public_main_residency`. Renewal follows existing acceptance/schedule evidence and coverage ordering; it is not a second onboarding.
- Reject competing product records or identifier/idempotency ambiguity. Do not use a failed wave lookup as sufficient public authority. A pre-launch resident who later joins publicly must pass an explicit supported legacy transition; this design does not silently convert old unpaid wave records into paid public orders.

The two public products may use one implementation module with explicit branches, but require distinct sender principals. Sender authority cannot mint provider payment facts or alter prices.

## Capture timestamp and period semantics

The official [YooKassa OpenAPI specification](https://yookassa.ru/developers/api/yookassa-openapi-specification.yaml) defines `captured_at` as the UTC ISO8601 instant of payment capture. Coordinator downloaded and verified this primary source; the local copy `/tmp/early-bird-yookassa-openapi-20261030.yaml:3422` was independently inspected for this design. It does not establish that a missing capture fact can be substituted by notification receipt time.

The provider JSON already supports this fact: `packages/integrations/src/yookassa/contracts.ts:33,46` validates `captured_at` and maps it to `capturedAt`. `YooKassaPaymentVerifier.verifyPayment` (`verifier.ts:69–109`) performs fresh GET, checks bound payment ID/order metadata/mode/currency/amount/status/paid, requires capturedAt, and places it in branded event **occurredAt**. A new main proof field is unnecessary. `verifiedAt` currently equals occurredAt; do not reinterpret it as the local GET observation time.

The inbox already stores occurred_at, payload digest and verification identity, and compares these exact immutable replay fields (`expert-residency-provider-inbox-repository.ts:268–303`). However first coverage currently uses processing clock (`:376–382,532–538`). Change only the explicitly public cohort to use the verified successful payment capture instant. Expose the effective calendar date as `(captured_at AT TIME ZONE 'Europe/Moscow')::date`; retain the actual capture instant for timestamp coverage boundaries, not a fabricated midnight or receipt-contact captured_at. Renewals begin at the later of payment capture and existing valid coverage end. Wave coverage still starts January11 as already implemented.

The public capture verifier must additionally reject capture before provider creation and contradictory temporal facts; the existing general verifier only requires presence while the onboarding verifier already compares capture against creation. Snapshot the immutable public product/operation/payment identity, amount/currency/mode, verified capture instant and source digest in PostgreSQL. A conflicting replay must fail, never overwrite the original capture. Missing or contradictory capture facts leave the public order unreconciled with an explicit diagnostic; never substitute webhook timestamp or database processing clock. Keep processing time for bookkeeping, lease/deadline checks and audit observation, independently of service-period origin.

## Deadline/credit race and uncertain-outcome recovery

A public payment captured on or before its authoritative payment deadline remains payable even when GET/webhook processing happens later. Compare the verified capture instant to the immutable deadline, independently of processing clock. Keep all genuinely late or contradictory payment facts for reconciliation; local time alone must neither forfeit an on-time payment nor manufacture an eligible one.

Existing expiry is shared: `expert-residency-repository.ts:327–342` exports `expireLockedExpertResidencyOrder`, which immediately expires pending orders and releases reserved referral credit. Its batch caller `releaseExpiredOrders` (`:577–603`) selects all overdue pending orders `FOR UPDATE SKIP LOCKED`. Other callers are `expert-campaign-order-repository.ts:268`, `expert-personal-offer-repository.ts:128`, the repository's command flow and provider inbox (`:387,416`). Therefore a batch-only filter is insufficient. Add the public-cohort unresolved-provider guard both at selection and inside the common locked helper, with equivalent SQL protection against any public expiry/release transition. Historical nonpublic behavior remains unchanged.

For public orders with a dispatched/unknown provider outcome, keep the reservation and exclude ordinary expiry until a fresh GET terminal fact, tied to the exact immutable operation/payment, has been admitted. The expiry/reconciliation command locks the same subject/order/operation/reservation set in the agreed order, rechecks the fresh terminal observation and current financial state, then either settles an on-time successful capture or releases on a proven unsuccessful terminal outcome. Pending, unavailable, ambiguous or unbound outcomes keep their uncertainty and reservation; do not release because LIST found nothing. Persist diagnostics/manual review for sustained uncertainty. A guard should reject direct release of an unresolved public reservation, rather than relying only on worker discipline.

If a reservation was already released, credit reused or competing coverage makes the verified capture inconsistent with financial state, atomically retain an immutable verified-paid fact and explicit manual-reconciliation disposition. Do not re-spend released credit, mint duplicate credit, silently discard the payment, or rewrite previous coverage. Only a later authorized reconciliation may resolve the inconsistency. Processing expiry must not erase the capture evidence. Add a dedicated new PG race file `packages/db/src/repositories/public-expert-payment-expiry-race.integration.test.ts`: pause provider discovery/expiry under controlled barriers, prove reservation preservation across deadline, settle on-time capture after processing delay exactly once, prove terminal cancellation releases once, and prove already-released/competing state yields immutable paid/manual evidence without balance corruption. Also exercise the nonbatch common-helper callers.

For unbound public CREATE and refund requests, discovery must be read-only. Reuse the bounded, pagination-complete LIST approach of `early-bird-list-recovery.ts`, but add explicit public purpose/snapshot matching rather than supplying fake wave fingerprints. Scan a bounded immutable creation window, require complete traversal and exactly one exact snapshot candidate, perform a fresh GET of that candidate and pass the branded proof to an isolated binder before settlement. Validate purpose, operation/order/subject, parent payment for refunds, mode, currency, amount and temporal facts. Empty, multiple, truncated, invalid-pagination, timed-out or transport-failed scans remain uncertain with no POST. Gateway currently has payment LIST and refund GET but no refund LIST; add the analogous strictly bounded read-only refund LIST endpoint if automatic unbound refund recovery is enabled. Do not claim existing refund GET can discover an unknown refund ID.

An audited existing manager-supplied provider ID followed by the same fresh GET and isolated binding is an optional explicit recovery operation, never an automatic fallback when a scan fails. The public cohort must be excluded from legacy exact-body POST replay: `exact-body-recovery.ts:76` retransmits uncertain encrypted operations, while `yookassa-operation-repository.ts:614–683` leases unbound replay candidates. Both selection and final replay admission must deny public CREATE/refund snapshots, so an old worker cannot replay a newly public operation. Known-bound capture/cancel needs only fresh GET of its exact parent payment to observe waiting/succeeded/canceled and its durable request outcome; do not re-POST after an uncertain dispatch.

All five outbound kinds in the endpoint table require a read-only financial authority contract for loading the immutable exact operation snapshot, plus a separate narrowly authorized state-changing admission/claim and isolated provider binder/settler. Read access does not imply send permission. Name the kind and cohort in each snapshot; the gateway must bind kind/path/parent/digest/idempotency to that snapshot and recheck fresh PostgreSQL authority, not infer purpose from an API-provided body. Capture/cancel cleanup remains independent of receipt-contact validity; contact-disclosing CREATE/refund retains the ACK fence. Add focused public unknown-create/refund recovery tests that demonstrate incomplete/empty/ambiguous scans never send or settle and a unique exact candidate still requires fresh GET and isolated binding.

### Lifecycle, collisions and transaction boundaries

Legal dispatch states: prepared → admitted → uncertain → bound → resolved. Abandoned is allowed only before admission with durable cancellation; an admitted send is marked uncertain before any provider write. A fresh failed admission performs no send. Loss of connection after admission/claim is uncertainty, not permission to reset to prepared. Parent-bound capture/cancel terminal GET may resolve their request without another POST. Observations can progress independently without rewriting the immutable request snapshot. Resolution is idempotent for the same identity/fact; conflict records manual disposition while preserving paid evidence.

Expected identity reuse is explicit: a public request links its existing legacy operation, invoice/order and subject, so those matching IDs are expected references, not collisions. The public request UUID belongs to a separate namespace; it must not collide with a wave intent/deferred invoice, unrelated legacy operation or another public request. A legacy provider operation already linked to this request is an exact replay only if user/product/kind/amount/mode/idempotency/digest all match. Any competing source, wrong owner, reused idempotency, alternate parent or conflicting provider object rejects. Do not blanket-reject all legacy invoice/order existence as the wave branch does: public cohorts intentionally reuse those financial records.

Never call gateway admission/POST inside the existing held repository transaction or while holding its invoice/operation/consent locks. Its current dispatch surrounds network invocation with a database transaction; a new gateway PostgreSQL claim would need those same locks and deadlock. Replace the public execution boundary with: transaction prepare/source locks → commit; fresh GET as needed → verified observation commit; transaction admit/uncertainty marker → commit; gateway fresh claim in its own transaction → provider send; response/GET → isolated bind/observe/resolve transaction. After every lock wait recheck fresh eligibility. Contact ACK/fence serializes PII send versus revoke; DB locks alone do not implement the approved ACK guarantee.

### Typed API and gateway contract

Public checkout ports implement the existing application outputs: onboarding `createCheckout({invoiceId})`/`recoverCheckout({invoiceId,operationId})` returns ready URL/payment ID or existing unavailable/pending outcomes; main `createOrRecover(binding)` returns `{kind:'ready',orderId,paymentId,url}` or `{kind:'pending'|'unavailable'}`. Add a separately typed held lifecycle `reconcile(invoiceId)` and bounded worker scan, and a refund port consuming an existing authorized refund operation, returning bound refund ID/pending without treating POST response as settlement. Port ownership checks still derive from the existing authenticated service command; all typed outcomes are validated before presenting a link.

Public IPC command is a dedicated operation `{op:'public_dispatch',request_id,user_id,idempotency_key,kind,contact_id,subject,attempt,request}` over the same authenticated channel. It contains no URL/path/parent identifier chosen by the API. Under the appropriate gateway fence, the new claim function returns the strict authoritative public snapshot using request/user IDs, requires exact kind/digest/idempotency/body equality, and exposes only the bound kind/parent needed to derive the permitted path. The gateway derives that path from returned row kind and row parent_payment_id immediately before writing; NULL or malformed result sends nothing. Request bytes may not smuggle a different request line: canonical header/path serialization belongs to gateway. Derive attempt token from idempotency and contact subject token as today when contact exists. Capture/cancel have contact_id=null and no contact subject; permit them only through their separate persisted financial authority and operation fence. Null contact is forbidden for onboarding/main create or any refund carrying a fiscal receipt. No generic arbitrary non-PII bypass is introduced.

### Refund metadata identity prerequisite

Official YooKassa OpenAPI `Refund` includes metadata (downloaded primary source line4524). Existing gateway `provider_reader.py:149–165` and transformed `yooKassaRefundSchema` drop it; existing general refund serialization also does not establish public operation metadata. No exact unique public refund identity can be inferred from matching amount/parent/time alone. Legacy refunds lacking this metadata stay on their existing reconciliation path or explicit audited manager recovery; do not invent metadata or weaken public recovery matching.

### Parent mutation fence and cumulative refunds

Capture and cancel have distinct request/idempotency IDs but mutate the same held provider payment. At admission and gateway claim, lock the canonical parent/invoice authority and serialize all active parent mutation requests.
