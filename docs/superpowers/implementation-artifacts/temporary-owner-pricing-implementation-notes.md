# Temporary owner expert pricing — implementation notes

Status: investigation, not implemented or enabled. The owner selected one production test expert and prices of RUB 10.00 for onboarding and RUB 20.00 for the monthly subscription. In the early-bird immediate-payment scenario the single provider payment is RUB 30.00 with two receipt items; the separated-payment path uses RUB 10.00 and RUB 20.00. The exact expert identity and production deployment are not inferred here.

## Required boundaries

- A versioned, durable, narrowly scoped grant must bind the specific internal user and live provider mode to this policy. It must be off by default and must not derive authorization from Telegram input, application text, a request parameter, or a caller-provided amount. Issuing/revoking this grant must use audited administrative authority. Preserve an immutable policy snapshot on each invoice so revocation cannot reinterpret an in-flight payment.
- Ordinary users, legacy orders, old facts, and provider observations retain their original prices and exact validation. A retry must reuse the original provider idempotency key and invoice snapshot; a changed grant must not alter an existing invoice.
- Include purpose, grant/policy version, amount components, recipient, operation, provider object and mode in the stored immutable binding. Verify provider GET and settled amount against that binding. Record late, revoked-before-admission and otherwise ambiguous outcomes for reconciliation; never fabricate onboarding or subscription payment facts to satisfy old guards. Preserve consent and deletion-before-first-send fencing. Actual payment verification is distinct from launch visibility.
- Restrict one-month term and exclude referral credit or other rewards unless their treatment is explicitly designed. A live test payment must not create unintended referral rewards or customer-facing publication before eligibility.

Prevent other users or a stale/revoked grant from selecting it. Keep ordinary pricing unchanged.
3. `packages/db/src/repositories/expert-held-onboarding-repository.ts` and `packages/integrations/src/yookassa/held-onboarding.ts`: replace literal request/receipt/capture amounts only in the narrowly bound test-policy branch; old bindings still require 3000.00. User-visible values must match the bound receipt; stale callbacks and unrelated users fail closed. Do not enable global flags as a substitute for missing composition.

## Evidence required before activation

- Focused domain/API/integration tests and PostgreSQL cases: authorized user vs unrelated/deactivated user, exact 1000/2000/3000 minor values and receipt items, combined vs separated flow, mode mismatch, amount/identity/metadata substitution, revoked and expired grants, immutable in-flight snapshot, repeated/concurrent webhook, provider unknown outcome, referral isolation, and no publication before coverage starts. Test old 300000/floor paths as regressions.
- Verify checkout can actually compose the live YooKassa client, verified payer receipt source, deletion fence, and provider verification in the production worker/API. Existing runtime-gap and receipt composition documents describe unresolved dependencies and need fresh exact-SHA evidence.
- Review the migration, provider and UI changes independently; run relevant typechecks, lint, `git diff --check`, and the repository-required exact-SHA deployment/database gates. Production mutation requires a separately authorized deployment with the selected user identity and rollback evidence. Merely toggling `PAYMENTS_ENABLED` or `YOOKASSA_ENABLED` neither supplies these checks nor scopes access.

The owner confirmed that the test expert account does not exist yet and will self-register. Therefore the scope must be assigned after registration through an authenticated, auditable, single-expert binding; it must not automatically enroll unrelated experts. No identity has yet been bound.
