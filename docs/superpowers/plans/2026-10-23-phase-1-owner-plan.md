# 📋 ФИНАЛЬНЫЙ ТЕХНИЧЕСКИЙ ПЛАН РАЗРАБОТКИ (PHASE 1)

## Проект «ии-Тоня» | Автоматизированный цикл резидентства

**Для:** ИИ-агента разработчика / Технического лида платформы `ii-tonya-platform`
**Статус:** УТВЕРЖДЕН. Приоритеты зафиксированы окончательно.
**Цель:** Реализовать сквозной, максимально автоматизированный процесс от входа эксперта в воронку до активации его карточки в базе знаний.
**Главный принцип:** **Автоматизация рутины + Человеческий контроль качества.**

- Система делает всё техническое: генерирует коды, считает рефералов, выставляет счета через ЮKassa, собирает данные, отправляет уведомления.
- Менеджер делает только то, что нельзя доверить машине: верификация личности/компетенций, утверждение контента карточки, ответы на нестандартные эскалации.

## 1. ИНСТРУКЦИЯ ПО РАБОТЕ ДЛЯ АГЕНТА (ПРОТОКОЛ КОНТРОЛЯ ХАОСА)

> **Внимание, агент!**
>
> Текущая проблема проекта — расползание сроков из-за отсутствия четкого графика приоритетов и попыток делать все параллельно без связи модулей. Этот документ устанавливает жесткий порядок действий.

### Правила исполнения

1. **База истины — существующий код.** Все промпты, скрипты диалогов и логика промо-воронки (`@ii_tonya_expert_promo_bot`) уже загружены в репозиторий и утверждены ранее. Твоя задача — **дополнить и связать** эти модули с новой бизнес-логикой оплаты и верификации, а не переписывать их с нуля. Если найдешь конфликт логики — используй команду `@conflict_alert`.
2. **Не жди отмашки на каждый шаг.** Выполняй задачи строго по порядку блоков Этапа 0 -> Этап 1 (Блок А -> Блок Б -> Блок В -> Блок Г). Как только этап завершен и протестирован локально — коммить в Git и двигайся к следующему блоку. Заказчик будет проверять статусы выборочно или по запросу `@status_report`.
3. **Заглушки вместо ожидания (Anti-Blocker Policy).** Если для реализации конкретного пункта (например, текст анкеты верификации или скрипт онбординга) нет точных данных от заказчика — создавай техническую заглушку (`TODO: Wait for Content Spec`), сохраняя структуру БД и API endpoints. **Не блокируй работу всего потока из-за отсутствия текстов.** Мы пришлем контент позже, ты просто подставишь его в готовые слоты.
4. **Терминология (Строго!).** Для экспертов: **«Бонусы»** (реферальные начисления), переменная `bonus_points`. Для клиентов: **«Купоны»** (внутренняя валюта сервиса), переменная `coupons_balance`. Не путай эти понятия ни в коде, ни в ответах бота.
5. **Сроки выполнения задач:** Максимально быстрые. Параллельная работа допускается **только внутри одного блока**, если задачи независимы. Переход к следующему блоку возможен только после закрытия критических зависимостей предыдущего.
6. **Взаимодействие с заказчиком.** Ты должен сам мониторить репозиторий и выявлять пробелы. Если информации не хватает для продолжения архитектуры — ставь заглушку и сообщай об этом через `@request_spec`, но не останавливайся.

### Команда: `@request_spec [Task_ID]`

Если не хватает данных для технической реализации: не останавливай работу, ставь заглушку и запрашивай спецификацию.

Пример: `@request_spec P1.C3` — «Для задачи P1.C3 нужны шаблоны текстов анонсов и изображений баннеров. Ожидаю файлы.»

### Команда: `@module_ready [Module_Name]`

Когда модуль протестирован и готов к merge — сигнал проверки качества.

Пример: `@module_ready Verification_Flow`.

### Команда: `@conflict_alert`

Если обнаружено расхождение нового плана с уже написанным кодом.

Пример: `@conflict_alert Logic in P1.A3 overrides existing tariff calculation script in promo_bot.py.`
