Classification method: a name is `LIVE` when `packages/config/src/env.ts` declares it in the Zod schema or when production code reads it from the process environment; `UNWIRED` when the name is present in `.env.example` and in documentation but no reader exists; `ABSENT` when the source requires it and no name exists anywhere.

## Headline finding

The configuration surface for Telegram, Selarti, Planerka, Google Sheets, Make, and the model providers is **declared but not wired**: 17 names exist in `.env.example` and in documentation, and setting any of them changes nothing at runtime because no production code reads them. Two further template names are read outside the schema and are deliberately excluded from that count: `NODE_ENV` (container and release scripts) and `EXPERT_REFERRAL_HMAC_KEYS_JSON` (`EnvironmentExpertCodeSecretResolver`, whose value never enters `RuntimeConfig`). Enabling an integration therefore cannot happen by configuration today — `packages/config/src/env.ts` fixes the eight integration switches to `z.literal("false")`, and the adapters are the disabled implementations that throw. `default-off` is verified, not assumed: all 29 `*_ENABLED` names in the template are `false`, all 29 exist in the schema, and `tests/repo/env-policy.test.ts` asserts both properties.

## Log redaction verification

`packages/observability/src/logger.ts` redacts through three layers: pino `redact.paths`, the `providerUrl`/`requestUrl` serializers, and a `logMethod` hook that walks every argument. Focused verification found three real leaks and the independent review found a fourth, all now fixed with regression tests:

1. A Telegram bot token outside a `/bot<token>/` URL survived untouched — only the URL shape was matched.
2. Provider key shapes (`sk_live_…`, `sk_test_…`, `pk_*`, `rk_*`) in message text survived.
3. Object keys `apiKey`, `password`, `passphrase`, `credential`, `secretKey`, `accessKey`, `signingKey`, `sessionKey`, `encryptionKey`, `masterKey`, `privateKey`, `hmac` were absent from the sensitive-key list, so their values logged verbatim; nested placement did not help because only the key name is inspected.
4. `botKey` / `bot_key` — the `CLIENT_TELEGRAM_BOT_KEY` field — was asserted to stay observable on the mistaken premise that it is a bot identifier. It is a bearer credential: the client webhook authenticates it with `secureEqual` and it is the request path capability. It is now matched by `bot[-_]?key` in the sensitive-key list. Redaction is log-time only (`sanitizeTelemetry` copies the object), so it has no effect on the value flowing through the app.

Known residual limits, recorded rather than hidden: the redaction list still has no generic high-entropy detector, a bare chat id is treated as a routing address and not as a credential, and a secret pasted into free-form message text is only caught when it matches a known shape. Non-secret fields ending in `Key` that carry identifiers (`idempotencyKey`, `requestKey`) are asserted to stay observable — a blanket `key` rule would have destroyed debuggability for 336 `idempotencyKey` call sites. `correlationId` also stays observable, but the client ingress derives it as `telegram:<botKey>:<updateId>` and persists that in `integration_outbox.correlation_id`; the credential in that stored value is not caught by name-based redaction if the object is ever logged, and changing the derivation is out of scope here because it is the DB dedup/idempotency scope key (asserted in `telegram-client-b1.integration.test.ts`) and `REQ-PLT-004.07` scopes to logs/prompts/commits, not the authority store.

## Access restriction and rotation

- Verified: `.env`, `.env.*` are gitignored with `!.env.example`; no `.env*` file is tracked; `.gitleaks.toml` allows only the `__PLACEHOLDER_*__` shape; every credential-shaped name in the template holds a placeholder; `validate-runtime-env.sh` rejects symlink or non-regular files, requires exactly one `NODE_ENV=production` and one `DATABASE_URL` with `sslmode=verify-ca|verify-full`, and rejects any runtime value containing a placeholder marker.
- **Open finding, not fixed here:** `validate-runtime-env.sh` never checks the **mode or ownership** of `/etc/ii-tonya/runtime.env`, which will hold `DATABASE_URL` with a password and any future provider credential. Suggested gate, to be applied only with operator approval because it can fail a live deploy and because `tests/repo/scope-boundary.test.ts` content-pins that script:
  ```bash
  mode="$(stat -c '%a' "$runtime_env")"
  owner="$(stat -c '%U' "$runtime_env")"
  [[ "$mode" == "600" || "$mode" == "400" ]] ||
    fail "runtime env must be owner-read only, got mode $mode"
  [[ "$owner" == root ]] || fail "runtime env must be owned by root"
  ```
- Removed in this change: `TELEGRAM_WEBHOOK_SECRET` was declared **twice** in `.env.example` (Telegram block and B2 block). Most parsers keep the last assignment silently, and the test helper `parseEnv` in `tests/repo/env-policy.test.ts` does the same, which is why it went unnoticed; `deploy/runtime.env.example` was checked and has no duplicates.
- Handed to the owner (task card step 3): the credentials that must be re-issued before any activation, by name only — `TELEGRAM_BOT_TOKEN`, `TELEGRAM_WEBHOOK_SECRET`, `TELEGRAM_CALLBACK_HMAC_KEY`, `SELARTI_API_KEY`, `SELARTI_WEBHOOK_SECRET`, `SELARTI_RESPONSE_SHARED_SECRET`, `PLANERKA_API_TOKEN`, `PLANERKA_WEBHOOK_SECRET`, `GOOGLE_APPLICATION_CREDENTIALS`, `MAKE_WEBHOOK_URL`, `LLM_API_KEY`, `INTENT_MODEL_API_KEY`, `EXPERT_REFERRAL_HMAC_KEYS_JSON`, and the `DATABASE_URL` password. **No external secret was rotated, created, or revoked by this task**; `Q-038` (storage and rotation mechanism) stays open and blocks choosing between an environment file and a secret manager.

Executable checks: `pnpm exec vitest run tests/repo/env-policy.test.ts packages/config/src/env.test.ts packages/observability/src/logger.test.ts tests/repo/gitleaks-policy.test.ts` and `python3 _bmad-output/specs/spec-owner-update-2026-09-16/validate_backlog.py --repo-root .`.
